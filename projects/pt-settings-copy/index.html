The argument in one line

We are not inventing a house style — three settings on this page already use the target shape (Apply payments to unpaid Invoice transactions, Apply Taxes, Apply expenses to unpaid Bill transactions). The other 18 each invented their own. This is standardising on what already ships.

The rules

  1. No conditional preamble. The switch already shows the state; the description states behaviour in present tense. A second sentence for the OFF state only where OFF is not the obvious inverse — on this page that is exactly one setting.
  2. “Synder does X” where Synder acts; passive only where it doesn't.
  3. One picker verb — Select. No “Please,”.
  4. No self-reference. A description never says “this setting” or “this option”.
  5. Dependencies leave the prose and become a stated requirement.
  6. “(recommended)” becomes a chip beside the label — grey .chip-neutral, not the coloured .badge-new.

The 10 shapes in use today

Each of these opens a toggle description somewhere on this one page.

“If you enable this setting (recommended)…” · “If enabled (recommended)…” · “If enabled…” · “If disabled…” · “It is an option to assign…” · “By enabling this configuration…” · “When "ON", Synder will be taking…” · “Enable this option to…” · “Enable this setting to…” · “If 'No' app won't receive…”
…plus three that use no conditional at all — the shape we are standardising on.

Findings that are not copy edits

  • The Auto-sync dependency is invisible. I set Auto-import off and Auto-sync on: no error, no warning, no blocked state anywhere. The only trace of the dependency in the entire product is the clause inside the Auto-sync description. Whatever else changes, that requirement has to survive — or the UI has to start saying it.
  • Two settings carry two descriptions each. Archive Pending transactions describes itself once on the switch and again on the days field, in different words. Apply Taxes has a short description and a longer one in the same row. Both need merging to one.
  • The Doc Numbers prerequisite is self-contradictory. “You should turn off custom transaction numbers… to disable this setting.” Two verbs for one act, a comma after “Please”, and arrows rendered as ->.
  • A revealed control explains the control that revealed it. Turning on Apply generic customer shows a picker whose help begins “If the generic customer setting is “ON”…”. The user has just done that.
  • Two settings have no description at all — Collect items for product mapping and Apply generic tax code. Both drafted here; both need a dev to confirm the behaviour I inferred.
  • Link affordances are inconsistent — page>>, Learn more >>, Build a Smart Rule >>. Should be a link plus →.
  • Plan-gate copy is a separate surface — “Upgrade to use” beside the switch, “This feature is available on higher plans.” plus “Upgrade plan” below. Not covered in this pass.
  • Dropdown help is its own mess — 22 dropdowns carry descriptions in at least four shapes: an instruction to the user (“Select available vendor or type new one”), the account’s role (“Track the sales of the inventory product on this account”), “App will transfer funds…”, and “Please, specify a category…”. How the capture was done

Every toggle was flipped individually and flipped back, plus seven ordered scenarios. Settings on this page save immediately on toggle (POST /v2/settings/…) — six such writes happened and all were reverted. A reload audit at the end confirmed all 21 toggles were back at their starting values.
