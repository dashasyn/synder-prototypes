Integration filter — match modes

Draft spec + working prototype. Organizations list, internal admin.

What changes. The Integration filter currently returns organizations matching any selected integration, with no way to say otherwise. This adds an explicit three-way match mode — Has any of / Has all of / Has none of — as a segmented control inside the existing dropdown. Nothing else in the filter panel changes.

The control

A segmented control at the top of the dropdown, above the search field.

  • Why not a separate operator dropdown in the panel. The panel is a two-column grid of one label, one control. A second control on this row breaks that alignment and makes Product and Company Country look inconsistent for not having one. Confirmed 2026-09-03: only this filter gets modes, so the heavier field + operator + value pattern isn't needed.
  • Why not radio buttons. Three stacked radios cost ~70px in a popover that already scrolls, and radios directly above a checkbox list read as more list rather than as a mode.
  • Order is mode → search → bulk buttons → list, so it reads top-down as one sentence: how to match, then what to match. Select All / Deselect All sit below the search because they act on what is currently visible, which only makes sense once the search is in view.
  • Always active. The mode is a standing choice, not a consequence of having ticked something — it stays operable at zero selections (where it has no effect yet) and survives clearing the list.

Markup is role="radiogroup" with three role="radio" buttons, roving tabindex, arrow keys to move, Home/End to jump. One tab stop for the whole group.

Closed-state label

This matters more than the control itself.

Today the field shows AFFIRM, EBAY. If the mode is Has none and the field still says that, the user reads the exact opposite of what is filtering. The closed value must carry the mode:

StateField shows
Nothing selectedAll integrations (placeholder grey)
1–2 selectedHas any of: AFFIRM, EBAY
3+ selectedHas any of 5 integrations
Mode = allHas all of: …
Mode = noneHas none of: …

The switch to a count at 3+ is deliberate: a truncated comma list combined with a negation (Has none of: AFFIRM, EBAY, AFTER…) is a genuinely dangerous string.

Naming

Use Has any / Has all / Has none, not Any / All / None.

The popover also contains a Select All button. A bare “All” segment sitting just above it collides: one means match every selected integration, the other means tick every box. The verb prevents that reading.

The filter is labelled Integration, matching the main interface. One check — the main interface's placeholder reads “All payment platforms”, but vocabulary.md reserves Integration and lists “payment platform” as a term to avoid. This draft uses All integrations. If the production placeholder is the one that's wrong, it's a separate copy fix — say which way to go.

Behaviour

RuleDetail
Default mode any — matches today's behaviour, so existing saved views and habits are unaffected.
Zero selections All three modes behave identically (no filter applied). The segmented control stays active — it is a standing choice, and greying it out reads as broken.
Apply-gated Mode and selection are draft state. Neither re-queries until Apply. Keep this — it is why there is no jarring mid-edit result flip.
Mode persists Changing or clearing the selection never changes the mode.
Dismissing the popover Click anywhere outside it, or Esc. No footer, no Done button.
Select All / Deselect All Two buttons, not a checkbox. They act on the currently visible options, so they respect an active search. Each disables when it would be a no-op.
Select All + Has none Legitimate — returns organizations with no connected integration at all. Not blocked.
URL / saved state Serialise the mode as …_mode=any|all|none alongside the existing integration selection parameter. Absent parameter means any, so existing saved links keep working unchanged.

Query semantics

Given selected set S and an organization's connected provider set P:

ModeReturns org whenSQL shape
anyS ∩ P ≠ ∅EXISTS (… provider IN S)
allS ⊆ PCOUNT(DISTINCT provider) FILTER (provider IN S) = |S|
noneS ∩ P = ∅NOT EXISTS (… provider IN S)

Note for whoever writes the query: none is an anti-join, not provider NOT IN (...). An organization with companies on both AFFIRM and STRIPE would satisfy a naive row-level NOT IN via its STRIPE row, and wrongly appear in Has none of AFFIRM. This is the single most likely bug in the change.

An organization with no companies at all has P = ∅, so S ∩ P = ∅ holds and it matches none — confirmed as intended, 2026-09-03. Worth stating explicitly because a NOT EXISTS anti-join gives this for free, while a JOIN … WHERE NOT IN silently drops it: the org has no company rows to join against, so it never reaches the filter. Same wrong query, second symptom.

Decided

QuestionAnswer (2026-09-03)
Does an organization with no companies match Has none of? Yes. “No company means also no selected companies.” Built in and asserted — Untouched Account appears under any Has none of selection.
Do Product / Company Country get modes too? No — integrations only. So the segmented control stays inside the popover; no field + operator + value rework of the panel.

One copy question is still open — see Naming above, on All integrations vs the production placeholder “All payment platforms”.

Out of scope

A single mode applies to the whole selection, so “has AFFIRM but not EBAY” is unreachable by design. If that turns out to be a real request the answer is not a fourth segment — it is per-row include/exclude (click once to include, twice to exclude), which is a substantially bigger build. Recommend shipping the three modes and waiting to see whether anyone asks.

The open popover overlays the Apply button, as it does in production today. Confirmed as acceptable — click away to dismiss, then Apply.
