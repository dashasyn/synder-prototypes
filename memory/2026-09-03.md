## Company provider — filter match modes (20:20–20:50 UTC)

Ignat, after an internal discussion: the `Company provider` multiselect on the admin
**Organizations** list needs three modes — all selected (AND), one of the selected (OR),
none of the selected. Asked first for suggestions ("radio button, selector, something
else?"), then "make a draft to share with devs".

**Answered: segmented control at the top of the existing popover**, above the search,
order mode → search → list. Rejected a separate operator dropdown (breaks the panel's
two-column label+one-control grid; makes the other three filters look inconsistent for
not having one) and stacked radios (~70px in a popover that already scrolls, and radios
directly above a checkbox list read as *more list* rather than as a mode).

**Naming call that isn't cosmetic:** `Has any / Has all / Has none`, not `Any / All /
None`. The list already contains **Select all** — a bare "All" segment six inches above
it means something completely different (match every selected provider vs tick every
box). The verb prevents the collision.

**The finding I'd rank above the control itself:** the closed-state field currently shows
`AFFIRM, EBAY`. Under a None mode that string says the *exact opposite* of what's
filtering. So the mode has to live in the closed label — `Has none of: AFFIRM, EBAY` —
and switch to a count at 3+ selections, because a truncated comma list combined with a
negation is genuinely dangerous.

**Real browser caught a real defect, again.** First verify run failed with Playwright
timing out on Apply: `.ms-pop-head … intercepts pointer events`. The open popover
physically **overlays the Apply button** — true in production too, and my mode row makes
the popover ~60px taller, so I made it worse. Added a **Done** button in a popover footer,
and then *asserted the overlap itself* so a future cleanup can't remove Done as
"redundant". This is the third time this month that the browser found something no amount
of reading the markup would have: [[feedback_verify_in_real_browser]].

**Dev-facing content on the page** (they get one URL, not a doc plus a link): query
semantics per mode, behaviour rules (default `any`, segmented disabled at 0 selections
since all three modes are then identical, Apply-gated, mode resets on clear,
`provider_mode=` URL param), and the warning that **`none` is an anti-join, not row-level
`NOT IN`** — an org on both AFFIRM and STRIPE satisfies a naive `NOT IN` via its STRIPE
row and would wrongly appear in "Has none of AFFIRM". Called it the single most likely bug
in the change, and asserted against it by name (Solvent Goods Co absent from the none-list).

**Two open questions left on the page rather than decided for him:**
- Q1 — does an org with *no companies at all* match "Has none of"? Strictly yes; probably
  not what the asker meant. Prototype excludes them, with a live toggle in the Q1 block
  that re-filters the table so the decision is visible rather than theoretical.
- Q2 — will Product/Country get modes too? If yes, the Jira-style field+operator+value
  pattern scales better and should be adopted now instead of the segmented control.

**Stated as out of scope:** one mode applies to the whole selection, so "has AFFIRM but
not EBAY" is unreachable by design. The answer would be per-row include/exclude, a much
bigger build — ship three modes and wait for demand.
