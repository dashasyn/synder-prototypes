## Juke box — V1 rebuilt as the schedule-first variant (19:12)

He picked V1 (events) as the variant to continue with, and answered all six questions. The model
that came out of it: **an event *is* a schedule** — period + sources + stations.

- **Several daily windows per source, and several sources per event**, each with its own weekdays:
  "Klassik Mo–Fr 09:00–12:00 + 15:00–16:00, Jazz Mo–Fr 18:00–22:00". The **kind is a property of
  the event**, not of each source — that turns "don't combine playlists and radio" from a validation
  rule into something the UI cannot express. Worth remembering as a pattern.
- **Status stays** and is derived from the period alone; his reasoning is good — a Christmas event
  created in September must read *Geplant* without anyone setting a flag.
- **Overlap warns, never blocks**, and only at **equal rank** (radio vs radio). Different ranks are
  the intended case: playlist over radio is the whole point of the priority order.
- Period end optional = "offen" — that is how the always-on radio is expressed.
