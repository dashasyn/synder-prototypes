## Synder demo access SOLVED (12:25 UTC)

Got in. Working recipe, for next time:

1. **Cloudflare Access** — set the service token from `.synder-creds` as `extraHTTPHeaders`
   (`CF-Access-Client-Id` / `CF-Access-Client-Secret`). That alone is NOT enough: CF still
   demands an emailed OTP.
2. **OTP flow** — the code is bound to the browser session that requested it, so it must be
   request → relay → verify **without the browser context closing in between**. Request the
   code in one script that saves `storageState`, then verify in a second script that restores
   it. **Save storage state immediately after the verify click**, before attempting app login —
   losing the CF authorization cost two extra codes.
3. **App sign-in** — the email field is `input[type="text"]`, NOT `type="email"`. And
   `button:has-text("Sign in")` matches **"Sign in with Intuit"** first, which redirects to
   QuickBooks OAuth. Use an exact-text match on `Sign in`, or the submit inside the password form.

## Mapping — round 4, partial-save confirmed, recurring-task reframe (2026-08-07 12:26 UTC)

Ignat corrected the "mandatory, all-at-once" framing from round 3. Actual model:
1. Synder imports transactions
2. finds new transaction types
3. adds new mapping rows for them
4. those rows must eventually be mapped for summaries to sync correctly

So mapping is required *eventually*, not required *all at once* — and it's a **recurring task**
(new rows appear over time as new transaction types show up), not a one-time onboarding step.

**Verified live in the app** (with Ignat's go-ahead to change state, since testing partial save
required it): mapped 1 of 8 rows, and `Save mappings` went from disabled to enabled — confirming
**partial/incremental saving works**. Also found **Mapping status filter with All / Mapped / Not

supported concept, not something to design from scratch.

**This walks back the round-3 banner copy.** "8 groups need an account before your summaries can
sync" was rejected as too absolute (implies a single-sitting wall that doesn't exist). Revised to
reflect recurring nature:
> **2 new groups need mapping.** Synder suggests accounts for all of them — review before
> anything saves.
> `Review suggestions` · `Later`
Key changes from round 3: dropped the ultimatum clause entirely, added an explicit `Later` /
defer option since deferring is genuinely supported by the product, and emphasized the count
changes each time (2 vs 8 vs whatever) as the reason it belongs prominently in the copy.

**Because it's recurring, the missing dismiss control (found in round 3) is now a bigger problem**
than first flagged — a big colorful/promo-style banner appearing repeatedly every time a new
transaction type shows up will read as wallpaper/nagging by the third occurrence, unlike a
one-time onboarding promo. Recommended NOT making it a loud one-off promo design given this;
colorful is fine, but treat it as a recurring task indicator, not an ad.

not "automation" but "you don't have to manually pick from 167 accounts, 8 times (or 100 times)."
Also reinforces the round-3 recommendation to sort `(Synder)`-suffixed (newly created) accounts
first in review order, since spotting a wrong suggestion by eye is much harder against a
167-option list.
