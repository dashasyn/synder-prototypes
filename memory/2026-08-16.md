## Morning idea (2026-08-16) — ETC Notifications: lifespan, not filtering

Took the ETC Notifications open question framed as a filtering problem since v1: *"filtering at
100/day with no expiry?"*

The assumption baked into that question is that 100 items/day is a **finding** problem — give
the dispatcher better filters and they'll locate what matters. Reframe: it's a **lifespan**
problem. Most of those notifications describe an event that stops being true — a delay alarm is
meaningless once the train arrived; a device-offline alert is noise once it reconnects. If
nothing ever leaves the list, filters are just a way of manually re-doing what the system
already knows.

What if each notification type carried a resolution condition, and the default view showed only
items still true? Then 100/day becomes maybe 10 live at any moment, and filtering is a
convenience rather than a survival tool.

Implementation is a rule table plus one segmented control on the existing list (**Active / All**),
not a new screen. It also answers a second open question: a list that self-clears reads as
actionable, while a permanent archive reads as read-only.

Next step if Ignat likes it: list the notification types and mark which ones have a natural
resolution event. The ones that don't are the real candidates for filtering.
