Fourth occurrence of this specific bug class in this thread.

## Filters v13 — production taxonomy + V6 control pass (13:30–15:0x UTC)

Ignat sent a screenshot of production's **grouped status dropdown** and answered the open list.

### The taxonomy question is closed
**19 statuses in 5 groups**: Ready to sync · Successful (Synced, Skipped, Excluded from sync) ·
Needs attention (Failed, Rollback failed, Synced with rule failed, Canceled, Rollback canceled,
Not parsed, Synced with warnings, Deleted with warnings) · Deleted · In progress (In progress,
Scheduled, Rollback in progress, Rollback scheduled, Pending, Delayed).

Two corrections to the stand-in I'd been using since Aug 4: **"Rule failed" is really "Synced with
rule failed"**, and **"Synced with warnings" belongs to Needs attention**, not Successful. I'd
guessed the second one right in SEGMENTS but wrong in STATUS_GROUPS — worth noting that a guess
can be right in one place and wrong in another when the same fact is written twice.

### His answers to the blocked list
- #3 V8 pills single-select → **ignore**
- #4 Is/Is not → **keep as is** (don't build)
- #7 date chip not saying "system selected" → **fine**, what matters is that the filter reads as
  applied. That answer is what made the `Clear filters` visibility decision easy.
- #2, #6, #8 → "I don't understand" (answered in chat, no code)

### Decisions
- **SEGMENTS built from the group map**, not hand-listed, so the tab row can't drift from the
  dropdown. Kept *Needs attention* first rather than mirroring the dropdown order (which lists it
  third) — a dropdown can bury the 986-clicks-a-month item, a tab row shouldn't. Flagged as mine.
- **Dataset 26 → 45 rows** so all 19 statuses appear. A taxonomy demo where 11 statuses read zero
  demonstrates nothing.
- **Badges coloured by group, not per status.** 19 colours = 19 things to keep in sync. Two
  overrides: *…with warnings* amber (a warning is not a failure), *Skipped / Excluded from sync*
  grey (a deliberate non-sync is not a success).
- **"All …" rows removed from chip-style fields only.** His reasoning was the dedup argument: the
  × already clears. But select-style fields (V1's bar, the sheets) have no ×, so they keep the
  row. The asymmetry *is* the justification — removing it everywhere would make date unclearable
  in V1.
- **`Clear filters` clears to nothing-applied**, not back to the 90-day load state. A "clear" that
  leaves a filter behind isn't clear. It renders only when something is applied — and because his
  #7 answer says the 90-day chip should read as applied, the button showing on load is now honest
  rather than the lie the old *Reset-on-a-clean-page* finding was about.

### The nice part
**V8's pills-vs-dropdown threshold is finally doing real work.** I built it on Aug 20 as a guess
at what a ~18-status taxonomy would force. With the real groups: Successful (3) → pills, Needs
attention (8) and In progress (6) → scoped dropdown, Ready to sync and Deleted (1 each) → no
second level. `V8_PILL_MAX = 4` is the only knob, exactly as designed.

### Test lesson (a new one)
**Every one of the eleven suites hardcoded the 8-status taxonomy, so all eleven broke at once.**
Roughly two hours of the session went on test surgery. They now **parse `STATUS_GROUPS` out of the
source** and derive group membership from it — the same principle the row oracle already used for
the dataset, just never applied to the taxonomy. **A constant copied into a test is a second
source of truth waiting to drift.** If a fact lives in the source, parse it; don't retype it.
