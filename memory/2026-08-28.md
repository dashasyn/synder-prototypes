## ETC optics+timing — one table instead of two (11:45 UTC)

Ignat pushed back on the timing screen: *"Why did you create 2 tables here? Why not one. The top one
with some columns from the bottom (Based on and Time source)."*

**My answer, and where he was right.** The two tables had different keys — a station has one set of
lead times but several trigger rows (1820 has two, one per platform). A flat merge duplicates
`-2:00` onto both rows. But he was pointing straight at the ticket's own open question 3
(override granularity), which my assumption A1 had answered one way. If the finer grain wins, one
table is simply correct.

Two things his exact sketch couldn't do: **"Based on" can't travel without Optic ID / 2806 type /
offset** (four fields move as a unit → 11 columns with structurally empty cells, i.e. the disease
we just cured on the notifications table); and **"set this whole station" stops being expressible**,
because trigger rows only exist for configured exceptions.

**Resolution — nested, not flat.** One table keyed by station. The station row carries the three
lead-time values; expanding it reveals that station's trigger rows plus a scoped "+ Add trigger at
<station>". Keys stay clean, no duplication, one place to look, and the visual hierarchy matches the
data model. He asked for the rewrite directly rather than a side-by-side, so the two-table version
is gone.

Also: 1820 starts expanded so the nesting is self-evident; adding a trigger auto-expands its
station; the optic cross-link expands the target station before opening the row.

**Verified:** 21 DOM assertions, all passing, 0 JS errors, no horizontal overflow. Covers
expand/collapse per station, the no-trigger message, lead-time editing and reset from the station
row, the nested trigger editor with the shared control, station preselection when adding from a
station's own button, and the optic cross-link out of a nested row.

**Lesson worth keeping:** he was challenging a structure I'd justified on data-modelling grounds,
and the honest answer was "you're right that it's clunky, wrong that a flat merge fixes it" — the
third shape was better than either of our first two. Answering "here's why I did it" without also
looking for the better option would have been the weaker response.

   different: 15 `<option>` elements had **no `data-i18n` attribute at all**, which is why

2. **"Step-3 summary concatenates the filter values"** — the chips are a flex row with a 5px gap and
   never overlapped. I read it via `textContent`, which has no spaces between elements. Screenshot and
   `getBoundingClientRect` both disprove it.
   → **Lesson: `textContent` is not a layout observation, and a regex over a JS object literal is not
   a parser.** Both classes of error produced confident, specific, wrong findings.

**Notable fixes and their root causes:**

**Two bugs I hit while building — both classes I had already fixed elsewhere today.** Worth
remembering as a pattern, not a one-off:
1. **Re-render + document click handler = panel closes.** Clicking a day re-renders the calendar, so
   `e.target` is detached when the document handler runs and `closest('.rd-range-wrap')` returns
   null → the picker closed on the first click. Identical to the Kantone panel. Fixed with the same
   `if (!e.target.isConnected) return;` guard.
2. **Row click doesn't flip its own checkbox.** "Alle auswählen" read `.checked` on a box the row
   click never toggled, so it always saw false. Identical to the schedule toggle row. Fixed with a
   `rdDirRow()` wrapper that flips the box first.
   → **Lesson: when a click handler reads `.checked`, check who actually flipped it; when a list
   re-renders on click, check what the document-level handler sees.** Both produce "the control
   does nothing" with no error in the console.
