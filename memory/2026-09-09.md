### Two mistakes worth keeping

1. **A balanced global div count proved nothing.** After the first pass, opens−closes over the
   view segment came out to exactly 1 (the view div) — looked correct. It wasn't: the TU row
   was missing its `</div>` and a later row had a spare, so the two cancelled. In the browser,
   rows 3–6 nested inside the TU row and spilled outside the card. **Assert structure, not
   totals**: `filter-section > .filter-row` direct-child count, `.filter-row .filter-row`
   nested count = 0, one `.filter-control` per row.
2. **`showView('rohdaten')` is not the entry point** — `showRohdaten()` is, and it seeds the
   date range, the TU/lines/stops lists and the note. Driving the view directly gave an empty
   Zeitraum field and an empty note box that I nearly reported as bugs. Same class as the
   "recon choices are coverage claims" lesson: **enter through the route a user takes.**
   Also: `rdRun()` adds the export inside a `setTimeout`; a 700ms wait read as "Run is dead",
   a 3000ms wait showed 3→4. Don't call something broken on a short wait.

Also caught and fixed before shipping: constraining `.rd-config` to 800px clipped the
"Erstellte Exporte" params strip. The produced-exports list is a *result* list — moved back
outside the wrapper to full width, like the evaluations list.

Verified in real Chromium (system `/usr/bin/chromium-browser`; bundled Playwright chromium is
not installed, and `file://` is blocked — serve over `python3 -m http.server`): real route via
New Evaluation → card, 6 sibling rows, row metrics byte-identical to the wizard's, dropdowns
and range picker open, picker survives a day click, threshold guard fires (`.input-error`),
Run produces an export, DE + EN labels correct, no console errors.

MUI is React-only, so it cannot be dropped into this file — the question is really which of

- **C. React + MUI rewrite** — real MUI incl. DataGrid / DatePicker / Autocomplete, but a full
  rewrite of 16 views plus a Vite build and a changed deploy, and all 37 review fixes and the
  i18n layer have to be carried over and re-verified

Asked Ignat to choose. **Awaiting answer — do not start.** Flagged the consequence he may not
have priced in: the current styling was calibrated against production Q-Explorer screenshots,
so going Material means the prototype stops matching production and fidelity comparison dies.

## MUI question answered: MD2 confirmed, and a licensing finding

Ignat: "Our developers will use material design 2 MUI library for sure. So I want to show them
something similar to the final result. It is a difficult token consuming job?"

Two things settled by that:
- **MD2 eliminates Material Web** (`@material/web` is MD3). So the choice is only
  CSS-restyle-to-MUI-specs vs full React+MUI rewrite.
- **Purpose is a developer handoff artifact**, not a production step. That reframes it: fidelity
  to MUI's *default* look matters, using the actual React library does not.

Cost given to him: restyle ≈ one session (volume, not difficulty — ~2,160 CSS lines to MUI's
default theme; no JS changes so nothing needs functional re-verification). Rewrite ≈ several
sessions, and the real cost is re-implementing and re-verifying all 37 review fixes and 572
i18n bindings, i.e. re-earning ground already held.

### Licensing finding — the valuable part, verified at https://mui.com/x/introduction/licensing/

Three of the prototype's signature features fall in MUI X's **paid** tiers:
- **"Aufschlüsseln"** (3-level breakdown) → DataGrid **row grouping** → **Premium**
- **Zeitraum two-month range picker** → **DateRangePicker** → **Pro**
- **27 column filters** on the raw-data table → **multi-filtering** → **Pro**

Free Community DataGrid = single-column filtering, no grouping. Either the budget carries a
per-developer licence or those three get hand-built. Raised with Ignat before the devs start.
