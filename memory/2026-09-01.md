## Lesson: blur re-render swallows the next click

Found in real Chromium, not jsdom. Editing the DE text then clicking "Audio erzeugen" did nothing
on the first click: `onblur` fired on the button's mousedown, ran a full `render()`, replaced the
button node, and `mouseup` landed on a fresh element so no click event fired. Playwright's
`.click()` doesn't fail on this — it clicks happily and the handler never runs, so the only way it
surfaced was asserting the *resulting state* ("DE audio ready") rather than the click itself.

Fix: `commitEdit()` only records the edit. Everything text-dependent updates in `oninput` through
surgical DOM updates (`renderMsgMeta`) that never replace the textarea.

Two rules for next time:
1. Never call a full re-render from a `blur` handler.
2. After a UI action in a test, assert the state the action was supposed to produce — never assume
   the click landed because the click call returned.

## Synder — Configurable payment application engine (SD-16243 Iteration 1)

Ignat sent the Confluence FDD `[Settings] Configurable payment application engine` (page
3160113208) and asked for two things: explain it in simple words, then build a prototype.
Explanation went into Telegram (topic "Payment settings"); prototype is
`projects/payment-application-engine/index.html` →
https://dashasyn.github.io/synder-prototypes/projects/payment-application-engine/

Full detail in `PROJECTS.md`. The one thing worth remembering about this feature: **the two-half
shape of the rule is not a preference, it's a QBO constraint.** QuickBooks' query language is
AND-only and can't filter on `PrivateNote`, so the only fields that can go in the query
(CustomerRef, TxnDate, DocNumber) become a fixed three-row *scope* that returns a snapshot, and
everything else — negations, "is empty", memo matching — is evaluated by Synder in memory against
that snapshot. Every odd thing in the UI follows from that: why scope's match row offers 4
operands and the condition box offers 10, why the date window matters for some configs and not
others, why row order can't be a combinator.

The three traps the FDD keeps repeating, all implemented and asserted:
- **Override, no fallback.** Engine on → default matcher never runs, not even as a backup.
- **Failed box ≠ scope-only.** Empty box (zero rows) + candidates → first in snapshot. Box with
  applicable rows that matched nothing, or all rows not applicable → process as usual. Applying
  to the first candidate in those cases would make the box a semi-condition (DL-35/DL-38).
- **Two toggles people will confuse.** Cancel-sync = nothing matched. Apply as overpayment =
  something matched but the payment exceeds the due. Kept in separate rows with explicit copy.

Verified in real Chromium: 86 assertions, 0 JS errors (`scripts/verify-payapp.cjs`).
Two bugs the browser caught that jsdom would not have: the `<details>` disclosures collapsed on
every re-render (open state now lives in `ui.open`), and the fixed overlay sat under the sticky
presenter bar (`--pbar-h` measured on load and resize).
