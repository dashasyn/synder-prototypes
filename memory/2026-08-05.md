### What I added to his diagnosis
- **It's structural, not cosmetic.** 39 of the 63 event-describing cells are `-` (62%); 40% of all cells. A table makes every type declare all
  14 fields when each type only uses 3–4. Platform changes use Station/Platform/Actual platform;
  delays use Delta; announcements use almost nothing. That's the horizontal scroll.
- **The columns duplicate the Text column.** "IC/32 3210 Train 10 to Haifa: The platform at Akko
  has changed from Platform 2 to Platform 4" already contains Title, Type, Station, Platform,
  Actual platform. Title ≈ Type — on two rows the strings are byte-identical.
- **Three kinds of thing in one list:** operational events (ARAMIS — platform change, delay,
  schedule deviation) · announcements (OPS — facilities, speed restriction, timetable) ·
  **system-health alarms** (data mapping failure, feed interruption). The third has a different
  audience than the first two. Raised as an open question rather than assuming.
- **Two real bugs in the current build:**
  1. Sorted by **time-of-day, ignoring the date** — 12:20 (5 Aug) → 12:55 (4 Aug) → 13:05 (5 Aug)
     → 13:30 (2 Aug). Sort key is a time field, not a datetime. Also ascending, i.e. oldest first.
  2. Pagination controls + "Rows per page 25" for 7 items, and the "Rows per page" label appears
     twice in the footer.

### Round 2 — real app chrome (11:41 UTC)
He sent two more screenshots: the actual **Events** screen and the notification panel in situ.
Rebuilt the prototype background to match — navy `#14274e` 34px top bar, train-swoosh logo,
nav Maps ▾ / Station view / Events / Journeys ▾ / Systems ▾ / Pax ▾, 32px navy icon rail,
exit icon top-right, Events filter row + `+ ADD EVENT` + the events table with
Active/Draft/Finished chips.

Three findings that only became visible with the real chrome:
1. **The bell is a permanently-red pill** with a warning triangle and the count. It reads as a
   standing alarm, so red carries no information. Built both variants with a live toggle —
   A: today's red pill · B: neutral bell, red only on the count badge. Recommended B.
2. **The current panel anchors to the left edge** and covers nearly the whole viewport for 7
   items. A 424px right sheet keeps the Events table visible behind it.
3. **The product is bilingual HEB/ENG.** Events carry "Text output HEB" and "Text output ENG",
   so notification text will be Hebrew for some users. Added `dir="auto"` on row and detail text
   and seeded a Hebrew notification — verified RTL resolves correctly in both. A hard-coded
   `dir="ltr"` list would have mangled it. I would have missed this without the second screenshot.
4. The Events entity already has **Active / Draft / Finished** — almost certainly the origin of
   his "New / Passed" tab instinct. Kept separate deliberately: event lifecycle is not
   notification read state.

### Aside (12:22 UTC) — token cost of screenshots vs prototypes
Ignat asked which is cheaper: generating screenshots or building prototypes. Answer given:
prototype **authoring** is the expensive step (~10k output tokens for the HTML), but editing
after the fact is cheap (hundreds of tokens per change). Playwright DOM assertions are cheap
(~1k/run) and should be the default verification method. Looking at a screenshot myself costs
1.5–2.5k input tokens each — cheap alone, adds up if re-checked after every tweak. Guidance for
future sessions: verify mechanically via DOM queries by default; only screenshot for genuinely
visual questions (spacing, RTL rendering, chrome matching); don't skip a visual check just to
save tokens if DOM assertions can't cover it. Ignat should keep sending real product screenshots
— they're high value (the RTL/bilingual finding above came directly from his chrome screenshots,
not from anything I could have inferred from text).
