### Aside (12:22 UTC) — token cost of screenshots vs prototypes
Ignat asked which is cheaper: generating screenshots or building prototypes. Answer given:
prototype **authoring** is the expensive step (~10k output tokens for the HTML), but editing
after the fact is cheap (hundreds of tokens per change). Playwright DOM assertions are cheap
(~1k/run) and should be the default verification method. Looking at a screenshot myself costs
1.5–2.5k input tokens each — cheap alone, adds up if re-checked after every tweak. Guidance for
future sessions: verify mechanically via DOM queries by default; only screenshot for genuinely
visual questions (spacing, RTL rendering, chrome matching); don't skip a visual check just to
save tokens if DOM assertions can't cover it. Ignat should keep sending real product screenshots
— they're high value (the RTL/bilingual finding above came directly from his chrome screenshots,
not from anything I could have inferred from text).

## "No transactions" rows — clickable or not? (2026-08-05 17:25 UTC)

(showing an empty detail) or non-clickable, given bulk actions must still work on them either way.

## Copy/placement — rule-creation requirement notice, top vs bottom (2026-08-05 19:43 UTC)

Ignat asked whether to inform users of a requirement during rule creation via a top banner or
inline (bottom-of-field) messaging, showed a screenshot with both present simultaneously.

**Recommendation: inline/bottom only — drop the top banner.** Reasoning:
- `DESIGN_RULES.md:51` already establishes field-level messages go below the field.
- The constraint (something like "applies to unpaid invoices only") is a property of specific
  fields (Tax, item, amounts), so inline lets the user map the message directly to the control;
  a banner forces mapping quoted field names back to the form.
- Caught a real bug: the banner referenced **'Tax Rate'** but the actual field label on screen is
  **Tax** — a banner quoting a nonexistent field name is worse than not quoting one at all.

**Inline treatment also needed fixing**: three amber warning icons were showing on an untouched
form — nothing was actually wrong, so amber (an error/warning color) was miscalibrated for a
neutral constraint. Recommended neutral grey 12px helper text instead, escalating to amber only
if the rule would actually affect a paid invoice. Suggested copy: "Unpaid invoices only" (3
words, fits without wrapping). Also fixed a preposition error — banner said "applied **to**
unpaid invoices" (correct) but inline said "applied **with**" (wrong) — inline should match the
banner's correct preposition.

**General rule stated**: banners are for describing the rule's *outcome/scope* ("this rule will
skip paid invoices entirely"), inline is for describing what a *specific control* does. Test:
does the message describe a control's behavior or the rule's overall behavior? Never duplicate
the same fact in both places.

**Other issues flagged in the same screenshot** (separate from the placement question):
- Unstyled developer strings leaking into the UI as content: "line custom", "Tax, item, amounts
  are", "line4" — look like raw section keys/placeholders, not written copy.
- "Submit" button uses dev language; should read "Update invoice".
- "Close" rendered as a filled dark-grey button, visually competing with "Submit" — secondary
  actions should be outlined/text style per design system.
- Modal title "Update Invoice" is Title Case; rest of product uses sentence case.
- "Please note that" filler phrase — recommended deletion, sentence unchanged in meaning.
