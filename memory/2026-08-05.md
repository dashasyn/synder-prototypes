### What I added to his diagnosis
- **It's structural, not cosmetic.** 39 of the 63 event-describing cells are `-` (62%); 40% of all cells. A table makes every type declare all
  14 fields when each type only uses 3–4. Platform changes use Station/Platform/Actual platform;
  delays use Delta; announcements use almost nothing. That's the horizontal scroll.
- **The columns duplicate the Text column.** "IC/32 3210 Train 10 to Haifa: The platform at Akko
  has changed from Platform 2 to Platform 4" already contains Title, Type, Station, Platform,
  Actual platform. Title ≈ Type — on two rows the strings are byte-identical.
- **Three kinds of thing in one list:** operational events (ARAMIS — platform change, delay,
  schedule deviation) · announcements (OPS — facilities, speed restriction, timetable) ·
  **system-health alarms** (data mapping failure, feed interruption). The third has a different
  audience than the first two. Raised as an open question rather than assuming.
- **Two real bugs in the current build:**
  1. Sorted by **time-of-day, ignoring the date** — 12:20 (5 Aug) → 12:55 (4 Aug) → 13:05 (5 Aug)
     → 13:30 (2 Aug). Sort key is a time field, not a datetime. Also ascending, i.e. oldest first.
  2. Pagination controls + "Rows per page 25" for 7 items, and the "Rows per page" label appears
     twice in the footer.

### Aside (12:22 UTC) — token cost of screenshots vs prototypes
Ignat asked which is cheaper: generating screenshots or building prototypes. Answer given:
prototype **authoring** is the expensive step (~10k output tokens for the HTML), but editing
after the fact is cheap (hundreds of tokens per change). Playwright DOM assertions are cheap
(~1k/run) and should be the default verification method. Looking at a screenshot myself costs
1.5–2.5k input tokens each — cheap alone, adds up if re-checked after every tweak. Guidance for
future sessions: verify mechanically via DOM queries by default; only screenshot for genuinely
visual questions (spacing, RTL rendering, chrome matching); don't skip a visual check just to
save tokens if DOM assertions can't cover it. Ignat should keep sending real product screenshots
— they're high value (the RTL/bilingual finding above came directly from his chrome screenshots,
not from anything I could have inferred from text).

**Data fix required first**: prototype had 3 invented statuses. Replaced with Synder's real 8

**Open decision for Ignat**: presets (V5) and segments (V6) commit on click, not staged like
V1–V4. Reasoning: a staged quick-filter costs 2 clicks, defeating the point for an action done

Flagged that this is his call to override.

## Naming question — "block showing created books objects" (2026-08-05 14:02 UTC)

Ignat asked what to call the UI block that lists objects created in books during sync (journal
entries, customers, products, other).

**Recommendation: "In your books"** — matches existing vocabulary.md term "Books" and a
production button already labeled "See in books" (confirmed via LogRocket click index same day).
Also true whether an object was created or matched/reused, unlike "Created in books" which would
misrepresent matched rows.

Avoided: "Objects/Entities/Records" (dev jargon, not accountant language), "Created in books"
(breaks if block shows matched items too), "Synced items" (conflates the sync action with its
output).

Flagged: if the block also shows per-item sync status (synced/failed/rolled back), "Sync result"
is the better header with "In your books" as an inner group label. Suggested grouping by type
with counts — "Journal entries (3) · Customers (1) · Products (2)" — plural, sentence case,
matching QuickBooks/Xero's own names for the types so labels survive the click-through.

**Question back to Ignat, unanswered as of this log**: does this block ever show matched-to-
existing items alongside newly created ones? That's the deciding factor for the naming.

## "Summary lines" table description (2026-08-05 15:43 UTC)

Ignat sent two screenshots of the Summary page (`Summary May 30 – May 30, 2026`, mzkt.by/Stripe,
status *Attention required · Not ready*): the **Summary lines (USD)** tab and the **Linked
Transactions** tab, arrow on the info line "Here is a list of transactions linked to this
summary. Some may have different dates, which is expected. Why dates can differ". He wants the
same treatment for Summary lines, replacing the bare date range heading. Asked me to check the KB.

**KB sources used:** [Close-Ready Summaries](https://synder.com/help/close-ready-summaries-aggregated-view-clickable-drilldowns-and-monthly-mode/)
(drilldowns) and [Understanding Mapping Groups](https://synder.com/help/summary-sync-understanding-the-mapping-groups/)
(where Description/Account come from). KB framing: each row is a journal line; stated purpose is
"proving the number — tie any total to the individual payments/refunds that compose it."

**Pattern extracted from the Linked transactions line:** what the table is → the one thing that
surprises people → link. For Summary lines the surprising thing is that each row is an
**aggregate, not a transaction**.

**Recommended copy:**
> Here are the accounting lines Synder will record in your books for this summary, grouped by your
> mapping settings. Each amount is a total — click a blue amount to see the transactions behind
> it. **How summary lines are built**

Alternates given: an "always a journal entry" version, and a tie-out-focused version that names
debits/credits and suggests comparing against the Stripe payout report before syncing.

**Three decisions handed to Ignat:**
1. "Accounting lines" vs "journal entry" — he said JEs "most of the times", so the generic term is
   safer; if it's always a JE, the JE wording reads better.
2. **Tense breaks after sync.** "Will record" is right while status is *Not ready*, wrong once
   synced. Either swap to "recorded in your books" on synced summaries, or go state-neutral
   ("Here are the accounting lines for this summary…") for one string.
3. Link target — Close-Ready Summaries ("How summary lines are built") vs Mapping Groups ("How
   lines are mapped"), depending on which question users actually ask.

**Unrelated finding on the same screen:** the grey block reads "No transactions have been synced
to your books yet. Synder is still collecting data for synchronization" while Summary lines shows
complete amounts and Linked transactions shows a real $30.00 charge. Technically consistent
(collected ≠ synced) but "still collecting data" reads as *incomplete* over a preview that's
clearly finished. Flagged for a separate look — **not yet picked up by Ignat**.
