Status filter usage — Platform transactions

LogRocket, last 90 days (≈2026-05-28 → 2026-08-26) · go.synder.com/transaction/list · sessions whose user email or user ID contains synder.com excluded · Galileo AI metrics + DOM inspection of the live app

Verdict on the main question: no, users do not select whole status groups. Exhaustive group selection is rare — 107 sessions clicked all three Successful statuses, 13 clicked all eight Needs attention, 106 clicked all six In progress. Meanwhile 1,391 sessions clicked exactly one Successful status (1,236 of them Synced alone). Single-status filtering outweighs whole-group selection roughly 13:1.

But read the next box before deciding anything — the current UI charges 8 clicks for a group and 0 for "everything", so this measures cost as much as intent.
The interpretation caveat that matters. In production the group headers in the status dropdown (li.dropdown-header: Ready to sync · Successful · Needs attention · Deleted · In progress) are not clickable — they have no <a>, no handler. There is no way to select a group in one action today. So "users don't select whole groups" cannot be read as "users don't want groups": selecting Needs attention costs 8 clicks plus Apply, while Select All (everything) costs one. The behaviour is consistent with people avoiding an expensive action.

Inside Needs attention, the two most-used members co-occur heavily:

Of the ~1,190 sessions clicking Failed, 688 (58%) also clicked Canceled. So multi-status selection within a group is real and common — it just stops at two of eight, not seven or eight of eight. Exhaustive selection of that group (13 sessions) is 50× rarer than the Failed+Canceled pair.

Not measurable: "exactly one member" for the 8- and 6-option groups (needs 7 or 5 AND-ed exclusions in one session definition — LogRocket wouldn't express it), and a true "two or more different groups" count (needs an OR of three conditions). The one cross-group figure that did build: Synced AND (Failed OR Canceled) = 261 sessions.

The dropdown is a bootstrap-select with an actions box — button.bs-select-all and button.bs-deselect-all sit above the option list.

Select All is used in more sessions (1,554) than any whole-group selection, and about as many as single-status filtering (1,391). Both average ~1.5 clicks per session.

On the "select all then deselect a couple" hypothesis: it can't be confirmed or denied from click counts alone. Deselect All is a clear-everything button, not a per-item deselect — deselecting one option is an ordinary option click, indistinguishable in the data from selecting it. What can be said: Select All is followed by some further option clicks often enough that its 2,430 clicks spread over 1,554 sessions, and Deselect All's 696 sessions are a subset of the same population. Confirming the pattern needs watched replays, not metrics.

Note: Select All in this control selects all 19 statuses, which is the same result as the default "All statuses" — so a share of these 1,554 sessions are using it as a reset, not to build a selection.

What this means for tabs on Platform transactions

  • Group tabs alone won't fit the observed behaviour. The dominant act is picking one status (Synced 1,236 sessions alone) or a pair within a group (Failed+Canceled 688). A tab row whose units are the five groups serves neither directly — Needs attention as a tab returns 8 statuses when the user wanted 2.
  • Tabs plus a status control inside the tab does fit it. That is exactly the V8 shape in the filters prototype: group tab narrows the universe, a scoped status control picks the 1–2 members. It also matches the 58% Failed+Canceled pair without making them hunt through all 19.
  • Do not read the low group numbers as low intent. Group headers are inert today; the cheap action is Select All. Cost explains a lot of this data.
  • Whatever ships, keep single-status fast. Synced alone is 1,236 sessions; anything that makes one status cost more than it does today is a regression for the most common case.

Method & limits

  • Galileo AI metrics over the LogRocket app vn4kxj/synder_test, 90-day range, with email does not contain synder.com AND user ID does not contain synder.com applied. One metric — Canceled row-badge clicks — was built without the exclusion and is flagged in place.
  • The badge/filter confound is real and only partly resolved. Every table row renders the same status words as <span class="label label-default not-synched"> Ready to sync</span> (note the leading space). Exact-text matching therefore fails on badges for most labels — Synced/Failed/Canceled badge counts returned 0, which means "not matched", not "never clicked". Only Ready to sync got a clean split (5,188 filter vs 3,740 badge, 1.4:1). Treat the text-matched label totals as upper bounds.
  • Distinct-session counts are capped at 100 sample sessions per event-count metric, so per-label session numbers above 100 are truncated. The session figures quoted here come from session-count metrics, which are not capped.
  • Two capitalisations of one status exist in the data: Ready to sync and Ready to Sync. Worth fixing regardless of this research.
  • Selectors verified by logging into demo.synderapp.com/transaction/list and inspecting the live DOM, not assumed.
