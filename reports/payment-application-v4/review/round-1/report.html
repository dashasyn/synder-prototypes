CriticalA11Y-1 a11y

Toggling almost any control in the configurator calls render(), which replaces the entire left-column DOM (document.getElementById('left').innerHTML = ...); none of these onchange/onclick handlers restore focus afterward, so the browser drops focus to <body> once the interacted node is destroyed and recreated.

Where: Every checkbox, radio and select inside the custom-rule panel (e.g. 'Customer matches the payment's customer', 'On the payment, take the value from', 'Refine row 1: comparison', 'Use custom rules', '+ Add condition', 'Remove refine row 1')

Impact: A keyboard or screen-reader user who picks a source, a comparison, ticks a row, or adds/removes a refine condition loses their place after every single change and must Tab from the very top of the overlay to reach the next field — for a task that requires configuring several such controls in sequence, this makes efficient completion effectively impossible.

Did: select a new value in 'On the payment, take the value from' (or tick any row checkbox / choose 'Use custom rules') via keyboard
Saw: source: ch('c-msrc', ...R()) and the equivalent handlers for c-cust, c-date, c-match, m-default, m-custom, ce-i, cs-i, co-i, ct-i, c-join, c-over, c-cancel, c-add, cd-i all call render(), which rewrites #left's entire innerHTML with no .focus() call afterward — contrast with renderSim()'s explicit sl.focus() and the c-days/c-mkey handlers, which use refresh() specifically to avoid destroying the focused node

Fix: After render(), re-focus the element that triggered the change (e.g. capture document.activeElement's id before re-rendering and call .focus() on the new node with the same id), the way renderSim() already does for the sample-payment radios and the way c-days/c-mkey avoid the problem entirely by not re-rendering on input.

HighA11Y-3 a11y

The document keydown handler for Escape explicitly ignores the key whenever the focused element is an INPUT, SELECT, or TEXTAREA, so Escape only closes the overlay when focus happens to be on something else (e.g. the close button) — which the state map's one successful Escape test used.

Where: Overlay-wide Escape key handler

Impact: Since most of the configurator's controls are text fields and selects, a keyboard user editing 'Which Stripe field holds the reference' or any of the source/comparison/target dropdowns and pressing Escape — the standard way to back out of a modal — gets no response at all, with no indication why, and must Tab away to a non-field element first or reach for the mouse.

Did: press Escape while focus is on the 'Which Stripe field holds the reference' text field (or any select)
Saw: source: `if (t && (t.tagName==='INPUT'||t.tagName==='SELECT'||t.tagName==='TEXTAREA')) return;` — the handler returns before calling requestClose(), so nothing happens; this is untested by the state map, whose only Escape pass started with focus on ov-close

Fix: Let Escape trigger requestClose() regardless of focused element type (blurring the field first if needed), or at minimum close any open native <select> dropdown on the first Escape and close the overlay on a second, so the shortcut never silently does nothing.
