Sync details ("Explain") — rethink

2026-08-26, layout proposals added 2026-09-04 · Dasha · evidence: demo.synderapp.com (4 transaction types, live) + 6 screenshots from Ignat + LogRocket, 90 days, external users only

Where the page is reached from, what actually varies between transactions, what the options are, and which one I'd pick. Two of my earlier claims were wrong and are corrected at the top rather than quietly dropped.

Corrections — Ignat, 2026-08-26 17:22

1. My headline was built on a false premise

I said: "nobody clicks Explain on a clean sync — they click it when a number looks wrong, so the error variants are the undesigned ones. Design Failed and Not parsed first."

Wrong. Ignat: "we don't show 'Explain' for failed syncs, because nothing was synced, so nothing to explain." Explain only exists where a sync actually wrote to the books. Failed / Not parsed rows never reach this page at all, so there is no Failed variant to design and my sequencing recommendation was void.

This also confirms my own observation that I mis-read: in the demo org, only Synced rows carried an Explain link — Ready to sync rows had none. I treated that as a data gap. It is the rule.

2. "Warning rows have no Object link" is not a defect

Ignat: "we can't show object if it wasn't created in the books." Correct — an Adjust Inventory row that was skipped created nothing, so there is nothing to link to. The empty cell is honest.

What survives from that finding is narrower: the message names a fix target ("Convert the product to inventory in your sales channel") and that is unlinked. The link belongs on the product in the sales channel, not in the Object column.

Scope, corrected

Explain answers exactly one question: "something was written to my books — what was it, and is it right?"

Every status that reaches it wrote something: Synced Synced with warnings Deleted with warnings Rollback scheduled / in progress. Statuses that wrote nothing — Failed Not parsed Ready to sync — have no Explain link and belong to the list's status + Retry path, not here.

That scope is right. The problem is not what the page covers. It is that within that scope, the answer is the hardest thing on the page to find.

The four problems

1. The answer is what's collapsed

The line that resolves "why is my P&L wrong" is "Account: Stripe sales — your sale was mapped to this income account". It sits two levels deep behind a 4px triangle. What's visible instead:

Invoice was created. · Payment was created. · Expense was created.

That's a receipt, not an explanation. A Payout's entire log is one row — "Transfer was created" — which says nothing the status badge didn't.

2. Warnings are the best copy on the page, and they're buried

Inventory adjustment synchronization for the product 'Linen Wrap Dress' is skipped as this product is not tracked as an inventory one. Convert the product to inventory in your sales channel for successful synchronization.

Object, reason, and fix. This is the "explain" the rest of the page never does — the pattern already exists and doesn't need inventing. But the status says only "Synced with warnings": never how many, never which. You read every row hunting the amber one, and in the Invoice-payment shape two of five rows start collapsed, so a nested warning would be invisible.

The "Deleted with warnings" case is worse — the amber row is General, the last row, below five green ones, and it carries the actual cause: "Authorization fail: Synder is unable to get response from a QuickBooks Online company as Synder has been disconnected from QuickBooks Online by a user." That is the whole story of the sync, in last place, in a row labelled "General".

3. Sync time is a third of the page and it's support-facing

"81% in QuickBooks Online query/posting" has no action attached for an accountant. Keep it — support needs it — but not above the fold.

4. The Rules block is a static advert

"Automate your processes with rules · Create a rule" — byte-identical on every sync, says nothing about this one. It occupies a full section.

What LogRocket says real users, 90 days

Run 2026-08-28. External customers only (email excludes synder.com, cloudbusinessllc, synder.service). 3 metrics over 10,511 sessions, plus 91 individually watched sessions. Percentages from the watched set are directional, not population figures. Detail: logrocket-findings.md

It kills one of my recommendations

I said "demote Sync time — it's support-facing and eats a third of the page." 86% of watched sessions scroll far enough to see Sync time and Rules. Reaching the bottom is the norm, not the exception. Scrolling past something isn't using it, but I can't justify "nobody goes down there" any more — that claim was mine and it's not supported.

The biggest problem isn't in my rethink at all

68% of sessions (7,129) open a /sync/show/ URL more than once in the same session. Session review shows the dominant cause is manually reloading while waiting for a sync to finish. The "Reload the page to see the updated status" banner I found in the rollback state isn't a rollback quirk — it's the page's default behaviour, and it's generating the single largest behavioural signal on the screen.

Fix: poll or push the status. Nothing else on this page moves that number.

What it confirms

  • The mapping rows stay collapsed. Only ~13 of 91 sessions touched the Sync log expand triangles. Inverting the disclosure stands.
  • The Rules advert is dead weight. Create a rule was clicked zero times in 91 sessions — while 86% scrolled right past it. Seen, ignored. Strongest evidence in the whole run.
  • Users click error text expecting it to explain itself. All three rage/dead-click instances were on static log text — a cancellation message, a "Business Validation Error", and the plain sync-ID. That is exactly the warning-promotion case, arriving as friction.

Caveats I'm not smoothing over

  • Click and scroll percentages come from 91 watched sessions, not 10,511. Directional.
  • The repeat-visit metric counts any /sync/show/ revisit in a session, not strictly the same id, so 68% slightly over-counts — and its email filter used only synder.service, so it is less strictly de-employee'd than the other two.

Options

Option A · Outcome first recommended

No new screens, no new data, no new endpoints.

  • One generated sentence at the top, from the log tree. Clean: "Recorded in your books as Invoice 26EC8A01-0209, 20.85 USD, income to Stripe sales." Payout: "Recorded as a Transfer to your bank register." Warning: promote the existing warning message verbatim — it is already the best sentence available.
  • Invert the disclosure. Account + Product open by default; object IDs collapse. Mapping is the content, ids are the reference.
  • Warning count in the status, and any row with a warning force-opens its parent.
  • Surface Transaction type to customers. Cheapest single improvement on the page — it's the field that explains the log's shape.
  • Demote Sync time behind a "Technical details" disclosure. Dropped — 86% of users scroll to it, so I have no evidence it is unwanted. Leave it; revisit only if a click metric shows it unused.
  • Auto-refresh the sync status. Added on the LogRocket evidence — 68% of sessions reload the page manually while waiting. This is now the highest-value item in Option A.
  • Make log error/status text expandable. Every rage and dead click observed was on static log text.
  • Replace the Rules advert with the rules that actually ran on this sync; offer "Create a rule" only when none did.
  • State-aware actions, and fix the destructive GET (below).

Option B · Two tabs — Outcome / Technical

Cleanest separation of the two audiences. Costs a real build, and puts the technical view one click further from support, who are its heaviest users. Worth it only if A proves insufficient.

Option C · Side sheet from the list

"Explain" opens a sheet over the transactions table with the outcome sentence and mapping rows; "Full sync details" links to this page. Keeps the user inside their filtered list. This complements A rather than replacing it — pair it with the transactions-table work.

The "Deleted with warnings" screenshot, read line by line 2026-09-04

One screenshot of the Sync log on a rolled-back sync. Six rows, five columns. It is the densest piece of evidence in this whole file, and it argues for the layout below better than my prose did.

It contradicts itself inside a single row

Row 1 reads Invoice · 26EC8A01-0209 · Show in QuickBooks · Canceled · "Invoice was created." The Message column is describing the sync; the Rollback status column is describing the rollback. Two events, opposite directions, one row, nothing saying which is current. The three rows that carry the newest information all say "was created".

I cannot tell you what "Canceled" means, and I've been reading this page for a week

In a column headed Rollback status, Canceled can mean the rollback was canceled (object survives in the books) or the object was canceled/voided in QuickBooks (rollback succeeded). Opposite outcomes for the customer's books. Same for Skipped on the two child rows — those objects were never created by this sync, so the honest value is nothing to remove, not skipped.

Rule: a status value must name its subject when two subjects are on screen. Rollback canceled / Nothing to remove.

The cause is in last place, under a label that means nothing

The row that explains the entire screen — "Authorization fail: Synder is unable to get response from a QuickBooks Online company as Synder has been disconnected from QuickBooks Online by a user." — is row 6 of 6, amber, and its Object type is General. Its Object info, Object and Rollback status cells are empty.

That is the tell: it is not an object, so it does not belong in a table of objects. Three empty cells is the table saying so. Every General row is a page-level event and belongs in an alert above the log, not as its last row.

The page offers five links to a system it just told you it can't reach

Every object row carries Show in QuickBooks. The last row says Synder is disconnected from QuickBooks Online. The page holds both facts and reconciles neither — all five links will fail. When the connection is known-broken, those links should be disabled with the reason on hover, and the reconnect action should be the only live control.

Two smaller ones

  • The Sync log's intro sentence is an advert — "review your Settings… you can also use Smart Rules Recipes" — sitting in the exact spot where a summary of this log should be. Same complaint as the Rules block at the bottom, but worse, because here it is above the error. Replace with 6 steps · 3 rollbacks canceled · 1 problem.
  • Copy bug in that sentence: configuration.You — missing space.

Layout proposals

All three are built. Open the prototype ↗ — one page, layout switcher and sync-state switcher at the top. Nothing is wired; it is structure.

Three, cheapest first. They share one move: the page currently orders sections by Synder's process (info → log → time → advert) and every layout below orders them by the user's question instead (what happened → what's wrong → what do I do → the detail). Nothing is deleted in any of them.

Layout 1 · Fix the frame, keep the table ship this first

No new components, no new data. Four structural edits to what already renders.

  1. Lift every General row into an alert above the table, and give it the fix action. This alone moves the cause from last place to first.
  2. Children open by default, ids collapse. Already recommended; this screenshot shows why — Income account: Stripe sales is the row an accountant came for.
  3. The object identifier becomes the link. Kills five identical "Show in QuickBooks" links whose accessible name is the same string five times, and frees a column. Disable them when the connection is known-broken.
  4. Message column becomes state-current. During and after a rollback it describes the rollback, not the original write. The original write moves into the row's expanded detail where it is history, not headline.

The Sync log is 1 to 5 top-level rows across every transaction type observed. A five-column table is a lot of chrome for four rows, and it is why the warning message — the best copy on the page — is squeezed into a cell that wraps to two lines.

Layout 3 · Two columns — outcome left, technical right the target

Today the page is one full-width stack, so the only way to rank anything is vertical order, and the only way to demote the technical half is to bury it. The LogRocket run forbids burying it — 86% scroll to Sync time. A right rail resolves that contradiction: the technical content stays visible without competing for first place.

What I'd do

Layout 1 now, Layout 3 as the target, Layout 2 only if warnings still don't fit. Layout 1 is four edits to existing markup and moves the cause of the page from row 6 to row 1. Pair either with the two items the evidence ranks above all of this: auto-refresh (68% of sessions reload manually) and surfacing Transaction type to customers.
