Kept — Critical and High

Critical4× corroborated1. The configurator cannot be operated by keyboard at all

With the rule switched off the overlay contains exactly three focusable elements — close, Cancel and Save. The master switch is a <span class="toggle"> with no role, no tabindex and no aria-checked, so it can never receive focus, so sections 1-3 are never rendered and there is nothing to configure. All six switches on the screen share that markup. Separately, every select and the day-count field computes an empty accessible name, because the visible labels are <span class="fld-l"> rather than <label for> — and on condition rows after the first, the label is emitted as an empty string, so those rows carry no label even visually.

Orchestrator re-check. Confirmed independently by the orchestrator: querying the overlay for focusables returns only ov-close, ov-cancel, ov-save while the engine is off; document.getElementById("c-engine").focus() leaves activeElement elsewhere; all six selects report labels.length === 0 and aria-label === null.
Fix
  • Make the master switch a real focusable switch (button with role=switch and aria-checked, or a checkbox) that responds to Enter and Space, so the sections it gates can be reached.
  • Replace every field-label span with a real label element bound to its control, and emit the labels on every condition row rather than only the first, visually hiding them after row one.
  • Use <input type="checkbox" role="switch"> under the visual, or add role="switch" + tabindex="0" + aria-checked + key handlers
  • Give them a real handler or drop the pointer cursor

High3× corroborated2. “Nothing is pre-filled” is false at the moment it matters

The non-editable reference card shown while the rule is off states “Nothing is pre-filled, so no existing configuration changes until you build a rule and save it.” Turning the switch on reveals a complete rule: all three scope rows on, a 90-day window, and one authored condition row — Invoice note is equal to Memo on statement — that the user never chose. Save is enabled immediately. Saving it commits a rule strictly narrower than the default matcher it replaces: invoices with an empty statement memo stop matching.

Orchestrator re-check. Confirmed: the card text matches, and on first turn-on the condition box holds 1 row with all three scope rows on.
Fix
  • Either start section 2 with no condition rows and the scope rows genuinely unset, or drop the Nothing is pre-filled sentence and label the revealed values explicitly as a starting point the user is expected to review before saving.
  • Either start section 2 with no condition rows and correct the sentence to describe only that the saved rule is untouched until Save, or keep the pre-fill and relabel it explicitly as a starting template the user must review.
  • Start section 2 as an empty condition box (the state R16 already defines) so first turn-on presents scope defaults only, or drop the sentence and state exactly what the starting rule contains.

High3. The panel whose only job is proof prints the same value for every source

“The exact request Synder will send to QuickBooks” always renders DocNumber = 'INV-1042', whatever “Take the value from” is set to, because the literal comes from a ternary whose two branches are the same string. The engine resolves the real value from the chosen source, so for the panel's own stated sample payment the clause would be 'ORD-88431' for invoice note, 'in_9f2c' for invoice id, 'sub_881' for subscription id and '' for payment note. The panel also always prints the DocNumber line even when the source resolves to absent — including a blank metadata key — where the engine drops the clause entirely.

Orchestrator re-check. Confirmed in source: const sample = s.match.source==='payment_meta' || s.match.source==='invoice_meta' ? 'INV-1042' : 'INV-1042';
Fix
  • Derive the previewed literal from the same resolve() call the engine uses, state the sample payment value for the selected source in the preamble, and when the source resolves to absent replace the DocNumber line with an explicit clause dropped note.

High3× corroborated5. “is empty” disables the field it tests and keeps the field it ignores

Choosing is empty or is not empty greys out the “On the invoice” select — the conventional signal that the field no longer matters — while leaving “On the payment” fully editable. It is inverted: the operand tests only the invoice-side value, so the greyed control holds the only field being checked, frozen at whatever it happened to be. Worse, the engine still resolves the unread payment source first and skips the whole row as “not applicable” when it is absent, and validation still demands a metadata key for a value nothing reads. On the FDD's own worked example B the row is discarded even though the sole candidate satisfies it. Two of the ten operands the spec mandates are effectively unusable.

Orchestrator re-check. Confirmed in the engine: the empty/not-empty test reads only the invoice-side value; the source is resolved before any operand check.
Fix
  • For the two value-less operands, disable and visually mute the On the payment select instead of On the invoice, keep the invoice target editable, and render the row label as the invoice's <target> is empty.
  • For value-less operands, enable On the invoice and hide or neutralise On the payment (skipping its resolve() and its metadata-key validation), and have plain terms state the invoice field being tested with no payment-side dependency.
  • Invert the gating for value-less operands — keep the On the invoice target enabled and disable the On the payment source instead — and skip the resolve()/absent check for the source on those rows so applicability is judged on the field the row actually reads.

High3× corroborated6. The shared cancel-sync setting has two different commit models — and the off state can be unsaveable

Both surfaces claim one value: “changing it in either place changes both.” On the GSP row the toggle commits the instant it is flipped. Inside the overlay it is a draft that only lands on Save and is silently discarded by Cancel, close or Escape — with no unsaved-changes prompt anywhere, so a whole multi-row rule also dies to one stray Escape. While any blocking validation error is present, Save is disabled, so a flipped overlay toggle has no commit path at all while still displaying its new value. The same validation runs regardless of the master switch, so a retained configuration carrying an error keeps Save disabled after the rule is switched off — the footer says “1 thing to fix before this can be saved” while sections 1-3 are hidden and no error field is on screen, which means the integration cannot be returned to the default matcher.

Orchestrator re-check. Confirmed: with a blank metadata key and the engine switched off, sections are hidden, no error field renders, and Save is still disabled with that footer message.
Fix
  • Make the overlay copy of this row behave identically to the GSP row by committing on flip, or drop it from the overlay and show it there as read-only reference text with a link back to the setting that owns it.
  • Commit the shared cancel-sync value immediately on click in the overlay too, independent of the rule draft and of the Save gate; if it must stay Save-gated, label it in place as a pending change and warn on Cancel/Escape that the shared setting will revert.
  • Gate validate() on the engine-on flag so that only an enabled rule blocks Save, leaving the off state always saveable while the configuration is still retained.

Critical5× corroborated7. Two accounting statements the screen cannot support

“Open invoice.” Three labels call the candidate set open invoices, while the query panel states there is deliberately no balance filter so a fully paid invoice can still be a candidate. In accounting an open invoice is one with an unpaid balance; applying a payment to a zero-balance invoice posts an unapplied credit rather than settling anything. “Processed as usual.” The no-match outcome — the default branch, and half of what the user came to understand — is never translated into a document, although the screen names document types everywhere else. Whether an unmatched payment becomes a Sales Receipt (recognising revenue a second time) or an unapplied customer payment decides whether income is overstated, and the screen does not say. Related: the inheritance helper frames a missing customer as a data-completeness problem, when the real consequence is that a payment can be attributed to whichever customer sits on the invoice the reference happened to match — and the scope operands include contains / starts with / ends with.

Orchestrator re-check. Both quotes verified against the rendered text.
Fix
  • Either add the Balance > 0 line to the query, or keep the behaviour and relabel the outcomes to "no matching invoice" plus state in section 1 that unpaid (open), partly paid and fully paid invoices are all candidates — the precise term "open" must not be used for a set that includes closed invoices.
  • Name the resulting document in both places, e.g. "the payment is processed as usual — Synder records it as a Sales Receipt and no invoice is settled", keeping the precise document term and putting any plain-language gloss in a tooltip rather than replacing it.
  • Replace "processed as usual" with the concrete result — e.g. "Synder creates a new sales receipt for the payment instead of putting it on an existing invoice" — in both the toggle description and the plain-terms step.
  • Replace processed as usual in this row with the concrete artifact Synder creates when the sync is not cancelled.
  • Reword to state the consequence — "the payment is attributed to the customer on the matched invoice, which may not be the customer who paid" — and warn when the Customer row is off while the invoice-number comparison is anything looser than "is equal to".

High3× corroborated8. The admin-gated date toggle is a silent dead click — the most corroborated finding in the round

All three independent UX passes landed on this one. When the organization is not admin-enabled for no-limit, the toggle on the date row renders at full opacity, pixel-identical to the live toggles directly above and below it, and clicking it does nothing at all — no state change, no message, no acknowledgement. The only differences are cursor:not-allowed and a small grey lock glyph. The same screen renders its other blocked toggle — the plan-gated master switch — dimmed at 50% opacity, so the user has already been taught that unavailable toggles look dimmed. This is KF-4 exactly: the onboarding stepper labels are the densest dead-click zone in the product because they look like navigation and are not.

Orchestrator re-check. Confirmed: three clicks leave the class as toggle on with computed opacity 1; the handler returns early.
Fix
  • Give the date toggle the same visibly non-interactive treatment already used for the plan-gated master switch, and keep the lock glyph plus the existing hint as the explanation.
  • Render this toggle in the same visibly disabled treatment already used for the plan-gated master switch, and on click surface the reason with an actionable next step instead of returning silently.
  • Give the gated date toggle the same dimmed treatment already used for the plan-gated master toggle.
Raised by: ux3:UX-1 · ux1:UX-4 · ux2:UX-2 — 1 independent lens (ux)
High3× corroborated9. Every exit path throws the rule away without asking, and the overlay is not a dialog

Cancel, close and Escape all discard the entire configuration with no unsaved-changes prompt and no undo. Escape is bound at the document level with no dirty check and no target check, so it also fires while a native select is open or a text field is being edited — which is the standard gesture for reverting an entry, and the overlay is built almost entirely from native selects. On top of that the overlay is a plain div: no role="dialog", no aria-modal, no accessible name, the page behind stays tabbable, focus never moves into it on open, and all four close paths leave focus on <body> rather than returning it to the button that opened it.

Orchestrator re-check. Confirmed: #ov reports role === null; pressing Escape mid-typing in the metadata key field closes the overlay and discards the rule.
Fix
  • Track a dirty flag from the moment cfg diverges from saved and route close, Cancel and Escape through a Discard your changes? confirmation, ignoring Escape when it is dismissing an open select rather than the overlay.
  • When the working copy differs from the saved rule, intercept Escape, close and Cancel with a Discard your changes? confirmation, and let Escape only dismiss that confirmation.
  • Give the overlay role=dialog aria-modal=true with aria-labelledby pointing at the title, move focus to the close button on open, contain Tab within it while open, and restore focus to the trigger on every close path.

High2× corroborated10. Blocking errors are neither announced nor findable

Each blocking error is a plain div.err with no id, no role="alert" and no aria-live; it is not referenced by the field's aria-describedby and the field carries no aria-invalid. Nothing is announced when it appears. Meanwhile the fixed footer reports only a count — “1 thing to fix before this can be saved” — while the offending row sits in a body that scrolls independently and may be far off screen, with no jump-to-error affordance, and the disabled Save button drops out of the tab order entirely, so a keyboard user tabbing forward from Cancel leaves the dialog without ever meeting Save or learning why it vanished.

Orchestrator re-check. Confirmed: the error div has no role, no aria-live and no id; the new condition key input has no aria-describedby and no aria-invalid.
Fix
  • Give each error an id referenced by the field aria-describedby with aria-invalid true, put the footer count in a role=alert live region, and keep Save focusable using aria-disabled instead of disabled.
  • Name the first blocking error in the footer message and make it a link that scrolls its row into view.

Picking a metadata source reveals a free-text “Metadata key” field with the placeholder e.g. invoices, and the rule cannot be saved until it is filled. Named gaps — what nobody could verify

Each lens reports what its own judgement needed and the recon pass did not record. These are results, not omissions — an unexercised interaction is invisible to every lens downstream, so it is stated rather than guessed.

  • ux1 — Escape while a native select is open was never exercised. The overlay is built almost entirely from native selects and the Escape handler is registered on document with no target or defaultPrevented check, so dismissing a dropdown with Escape may close the whole overlay and discard the rule - a much more frequent trigger for UX-1 than a deliberate Escape, but unverified.
  • ux1 — The plan gate was only observed from the GSP side, where Configure is disabled. The overlay own Starter error block and its Available on Pro and above footer are therefore unreachable by a real Starter user.
  • ux1 — The generic-customer warning is not recorded in the state map controls, so whether it appears at the right moment and whether it should block rather than warn is unverified.
  • ux1 — No loading, latency or save-failure state exists or was exercised - Save is synchronous in the prototype.
  • ux1 — Save was only exercised from a valid state. Whether the disabled Save plus the count-only footer message lets a user locate an error in a long scrolling overlay was not tested, and no jump-to-error affordance exists.
  • ux2 — condition row with is empty selected: the state map records only target_disabled_when_is_empty:true; UX-1 was verified by reading the render and engine code, not observed in the browser
  • ux2 — Starter plan: no pass checked whether any upgrade affordance exists elsewhere in the row or page
  • ux2 — blocked Save while scrolled away from the failing row was not exercised in the recon pass
  • ux2 — no loading or in-flight state exists for Save in this prototype — the real product async save, failure and retry states are unreviewed
  • ux2 — ALL/ANY with a single condition row: the control has no visible effect between rows but the default-open In plain terms text does change; dropped below the confidence floor rather than resolved
  • ux3 — Error findability was not verifiable: the map never records whether the inline error is in view when Save is disabled, and no short-viewport pass was run.
  • ux3 — The Generic customer state was never exercised in the state map; whether it should also affect the scope validity guard (FDD Q4 open) is unverified.
  • ux3 — Applies to this integration only could not be tested: the prototype exposes a single integration, so whether the shared cancel-sync value is also shared across other integrations is unknown.
  • ux3 — Condition rows with the same source and target were never exercised, so it is unknown whether the builder warns about a condition that can never be satisfied or one that duplicates a scope row.
  • domain — "Apply as overpayment" off with a payment larger than the invoice balance: the state map records only that the sync is cancelled, never what happens to cash that was received and settled, so whether the books end up short a receipt (and unreconcilable against the payout) is unverified.
  • domain — Partly paid invoices: no candidate table in the state map contains an invoice with a partial balance, so the books effect when the payment is smaller than the remaining balance is unrecorded — the screen only describes the payment being bigger.
  • domain — The fully-paid-invoice candidate claimed by the query disclosure was never exercised: the simulator snapshot only ever holds INV-1042 with 259.50 still owing, so no run demonstrates a zero-balance invoice winning the match.
  • domain — "Processed as usual": no state in the map records the document Synder creates on the no-match path, so the resulting ledger entry could not be confirmed from the prototype.
  • clarity — Save confirmation: the slice records no toast or post-save copy, so I cannot judge whether the user is told the rule is live and what it now affects.
  • clarity — Cancel: no copy is recorded for leaving the overlay with unsaved edits, so whether the user is warned about losing a half-built rule is unknown.
  • clarity — Hover-only text is not in the inventory — the locked "Compare against" field carries an explanatory title attribute that never appears as visible copy.
  • clarity — Starter (gated) state: no upsell or blocked-click copy is recorded, so what a Starter user is told is unknown. (Orchestrator note: the state map records the Configure button as disabled on Starter, so the agent's inference that it is 'active' is wrong.)
  • fidelity — The state map records outcomes only for the simple-charge and overpayment samples; example C and the cancel-sync-on outcome have no recorded verdict, so the prototype was exercised directly to confirm R17 three branches.
  • fidelity — The state map records cancel-sync as a shared value but not its commit semantics: the overlay copy is transactional while the GSP toggle commits instantly. One value, two commit models — below my confidence floor as an R18 violation, but unrecorded and worth a decision.
  • fidelity — The state map lists target_disabled_when_is_empty as a bare fact with no verdict; interrogating it produced FID-1.
  • fidelity — The engine-off-with-a-retained-validation-error path appears in neither the exercised controls nor not_exercised; it was reached manually.
  • fidelity — file:// and localhost navigation were blocked by browser policy, so live verification ran against the deployed copy after confirming it is byte-identical to the local file.
  • trust — overlay Cancel-sync toggle: the state map records it only as toggled in place, never toggled-then-closed-via-Cancel/Escape, so the discard behaviour is read from the handler rather than an exercised interaction
  • trust — admin no-date-limit entitlement revocation silently forces the date row back on; revocation against an already-saved rule was never exercised, so whether the user is told their saved rule was narrowed is unknown
  • trust — post-save acknowledgement: Save closes the overlay with no toast; no failed-save path exists in the prototype, so error and rollback behaviour on a real commit is unverified
  • trust — In plain terms never mentions the inheritance flag, so with Customer off the read-back is silent on customer attribution for a matched payment
  • trust — the query preview sample payment is hardcoded and unrelated to the user data; whether production intends real-data substitution determines how much of TRU-3 survives into shipped code
  • trust — Starter plan: reaching the overlay on Starter was never exercised, so whether a Starter user can open, edit and attempt to save a rule is unverified

Exercised here — a single ArrowUp fires change, re-renders the overlay body and replaces the input node, so activeElement drops to body and two further ArrowUp presses leave the value stuck at 91. The field cannot be stepped by keyboard and stepping it once ejects focus from the dialog.
  • a11y — Escape mid-edit: the handler is bound on document with no guard, so typing into the metadata key and pressing Escape — the standard gesture for reverting a text field — closed the overlay and discarded everything. The same happens after using ArrowDown inside a select.

  • a11y — focus visibility checked and passing: close, Add condition, remove row, both ALL/ANY buttons, the three summaries and the selects all render a visible ring. No finding spent here.

Two live bugs were found inside these gaps, by lenses that went past the map to the page: a single ArrowUp on the day-count field fires change, re-renders the overlay body, replaces the input node and drops focus to <body> — so the field cannot be stepped by keyboard and stepping it once ejects focus from the dialog; and Escape pressed while editing a text field (the standard gesture for reverting an entry) closes the whole overlay and discards the rule.
