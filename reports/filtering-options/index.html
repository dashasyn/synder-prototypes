Filtering Options

Exploring different filter UI patterns to reduce vertical space while maintaining usability. All eight variants filter the same 26-row dataset, using Synder's real 8 statuses. Every variant is Apply-gated — the list is only re-queried when you commit, never on each selection. Variant 6 is a recommendation rather than another layout option, and variant 8 is the one that combines quick group filters with precise per-status filtering.

Recommended for Synder

What the evidence points to, rather than another layout option. Three ideas, each answering a finding we already logged — see the reasoning below the prototype.

  1. Status becomes a segmented control with counts, because that's the one filter dimension users actually touch (986 tab clicks vs ~0 status-dropdown clicks in 30 days on Summaries).
  2. The 90-day window is shown as a labeled default, not as a filter, so an untouched page carries no filter chrome at all.
  3. Status has exactly one source of truth, so a granular status arriving from a dashboard deep-link can't silently contradict the segment on screen.

Transactions

Why status is a segmented control, not a dropdown

FLT-1 · LogRocketOn Summaries, the status tabs took 986 clicks in 30 days while the status dropdown took roughly zero. Users filter by status constantly — they just don't do it from a select. Production's own click index confirms the shape of the problem: All statuses, All types and All payment platforms are all logged as click targets, i.e. users open the dropdowns and mostly close them again.

So status gets the cheapest possible interaction and carries a count, which is the thing users are actually looking for ("how many are broken right now?"). The counts come from one aggregate over the same result set the list already fetches — not a per-click preview, so this doesn't smuggle the query cost back in.

Why the filters sit above the segments

Because the segment counts are computed from the applied filters. Filter to Stripe and Failed stops meaning "all failed transactions" and starts meaning "failed Stripe transactions" — the number above changes because of a control below it. Reading top to bottom, the effect arrived before its cause.

Filters first fixes that: they set the scope, the segments slice it, and each row explains the one beneath it. It also puts the tab row directly against the table it labels, which is what makes a tab read as a tab. The alternative — segments on top — only works if the counts ignore the filters, and then clicking "Failed 3" can return one row. We've spent this week removing controls that lie; that would add one back.

Why the 90-day window is a baseline, not a filter

Reset-on-clean-pagePlatform transactions loads with a 90-day filter for backend reasons, so "Reset all filters" is visible before the user has touched anything. That button is lying about what happened, and it makes "reset" ambiguous — back to nothing, or back to 90 days?

Here the default is a dashed, ×-less chip reading Last 90 days (default), and the count line says "last 90 days (default), no filters applied" rather than claiming a filter is on. Same query cost, honest UI.

Why status has exactly one source of truth

FLT-2 · CriticalThe bug you hit on Summaries: pick "Failed" in the dropdown, click the "Ready to sync" tab, and you get Ready-to-sync rows while the dropdown still says Failed. Two controls, one dimension, no sync between them.

Status here is a single value. A granular status arriving from a dashboard deep-link shows as From dashboard: Rule failed and the containing segment goes to a dashed "partial" state — narrower than the segment, and it says so. Clicking any segment replaces the granular status and drops the chip. The two can't disagree because there's only one of them. Try the Simulate dashboard deep-link button above.

What stages and what commits

Segments and deep-link removal commit on click — one click, one query, exactly what a status tab costs today. Every other filter stages inside its own dropdown: opening a panel snapshots what's applied, its Apply commits, and closing without Apply discards. Because staged state can never outlive an open panel, this variant needs no bar-level Apply and no unapplied-changes warning.

Still open

Segment counts need a status-count aggregate on the list endpoint. The 5 segments here collapse Synder's 8 statuses; the real product has ~18, so the grouping needs a product decision about which land in "Attention required". And two reset labels exist in production today — Reset filter and Reset all filters — which should become one.

Filters as Button + Side Sheet

One Filters button opens a right-hand sheet holding every filter, status included, with Apply and Reset at the bottom. Applied filters appear as read-only chips under the toolbar — they show what's on and can be removed, but not edited. All composing happens in the sheet; the chips are a summary, not a control panel.

No status segments here. The sheet is the only status control on the page, so there's still exactly one control per dimension — keeping a segment row as well would recreate the Summaries bug where the two disagree. That makes this the "everything in one sheet" shape, and the straight contrast to variant 8, which puts the same taxonomy into group tabs instead. Single-select panels (Date range, Amount, Customer) use radio rows so every panel in the sheet reads as the same kind of control.

There's also no "Showing N of M · K filters applied" line: the chips row already names every applied filter and the badge already carries the count, so the sentence was a third readout of the same state.

Group Tabs + Scoped Statuses

The answer to the question the other variants left open: how to have both one-click group filters (Attention required) and precise per-status filtering (Rule failed) without the two ever contradicting each other.

  1. The split is by scope, not by control type. Date, Platform, Type, Amount and Customer set the universe and sit above the tabs. The tabs slice that universe and carry its counts. Status narrows within the active tab only, so it sits below.
  2. Switching tabs keeps every filter the user invested effort in. Only the status sub-selection resets — and that one couldn't have carried over anyway, since Rule failed doesn't exist inside Synced. Even that comes back: each tab remembers its own status selection.
  3. A contradictory combination cannot be built. The status control offers nothing outside the active group, so Attention required + Synced — a query that provably returns zero rows — isn't reachable.

Where this came from

Shopify OrdersThe leading selector owns one dimension, and that dimension is then removed from "Add filter" — pick Unfulfilled and Fulfillment status disappears from the list. One source of truth by removal, no syncing required. It works because every leading value is a leaf: Unfulfilled is a fulfillment status.

Synder's quick filters aren't leaves. Attention required is four statuses. Copy the removal rule and picking it destroys the ability to see only Rule failed — the thing users do most. So this variant scopes instead of removing: the status control stays, but only offers what the active group contains.

Why the two levels can't disagree

FLT-2 · CriticalThe Summaries bug: pick "Failed" in the dropdown, click the "Ready to sync" tab, get Ready-to-sync rows while the dropdown still says Failed. Two controls, one dimension, no relationship.

Here the second level is a subset of the first by construction. A subset can narrow its parent but never contradict it, so the disagreement has nowhere to live. That's also the argument against the obvious alternative — leaving the tab row and a full status dropdown independent. That version lets the user build Attention required + Synced, where the tab says 8 and the list says none: FLT-2 in a new coat.

Why tab switching isn't destructive

Because only one filter is tab-scoped. Platform, Date, Type, Amount and Customer live above the tab row and are untouched by switching — those are the ones that cost effort to set. The status sub-selection is a single click, and it's dropped because it can't survive: there is no Rule failed inside Synced.

Even so, nothing is actually lost. Each tab remembers its own status selection. Narrow Attention required to Rule failed, go look at Synced, come back — Rule failed is still there. A remembered selection can't read as a mystery filter because the level it belongs to is on screen: the row is labelled Status in Attention required, the pill is lit, and the tab above it goes dashed to say the selection is narrower than the group.

Why the tab count doesn't shrink when you narrow

A tab count answers "how many are in here", not "how many am I looking at". If narrowing to Rule failed also rewrote the Attention required count to 1, the tab would stop being a place you can navigate to and the second level would have nothing to be a fraction of. The list header carries the fraction instead — "Showing 1 of 8 in Attention required".

Pills or a dropdown — and why both are here

Groups with a handful of statuses render as a second row of pills with counts: contradiction is structurally impossible, counts appear at both levels, and one click is one query — the same cost a status tab has today. The All tab holds all eight statuses, which is too many for a row, so it renders as a scoped multiselect dropdown with an Apply inside its own panel.

Both are on screen deliberately, because this is the one thing that depends on the open taxonomy question: production has ~18 statuses, not 8. Groups that stay small keep the pills; a group that ends up with eight members has to become the dropdown. The threshold is the only thing that changes.

Dashboard deep-links

A status clicked on the dashboard lands here and selects its own parent group, then narrows to itself. There is still exactly one status value on the page, so the arriving status and the tab row cannot disagree — the deep-link picks the tab rather than fighting it. A single-status group (Skipped) needs no second level, and doesn't render one.

This is the one case that gets a breadcrumb chip: From dashboard: Attention required › Rule failed. The user didn't set this filter, so it needs attributing and it needs one obvious way off. Where the user picked a pill themselves, the chip would just repeat the lit pill next to it — that was variant 3's duplicate-chips mistake, so it isn't rendered. The All pill is the way back up. The scoped dropdown on the All tab gets a chip too, since a trigger reading "2 selected" doesn't say which two.

What stages and what commits

Tabs and status pills commit on click — one click, one query. The scope filters above stage inside their own dropdowns: opening a panel snapshots what's applied, its Apply commits, closing without Apply discards. Staged state can never outlive an open panel, so there's no bar-level Apply and no unapplied-changes warning.

Still open

Pills are single-select, so "two of the four attention statuses" is only reachable through the All tab's dropdown. Making the pills multi-select would cost an Apply and the one-click speed that is the entire point — worth deciding rather than assuming. Also unresolved: the Is / Is not operator from Shopify ("Status is not Synced" currently costs seven checkbox clicks) is not built here, and the group counts still need a status-count aggregate on the list endpoint.
