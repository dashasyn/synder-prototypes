Reconciliation setup — six concepts, and one premise that has to change

Grounded in Synder's help docs, the Confluence functional specs, and the captured production API. Every idea below traces to a rule; where something is an assumption, it says so.

First: the number we wanted to show doesn't exist

"1,200 transactions are ready to reconcile" would be invented. There is no per-transaction reconciliation-readiness state and no such counter anywhere in Synder — not in the help docs, not in the functional specs, not in any captured API response. Reconciliation is run-scoped over a date range, not queue-scoped over a set of transactions. The only counts Synder produces are after a run: Matched, Discrepancy, Not matched (Missing in accounting / Missing in platform), Ignored.

This matters beyond accuracy. A headline volume number is a vanity metric — it tells the user how much data exists, which they already assume, and gives them no decision. We have shipped this mistake before: the "your most active integration last month" hint asserted something about the user that wasn't checked.

Evidence Sync statuses are defined per transaction (Ready to Sync, Pending, Delayed, Synced, Not parsed…) with no reconciliation-readiness member — Synder sync statuses. Post-run counts only: matchedCount · discrepancyCount · notMatchedCount · ignoredCount · missingInAccountingCount · missingInPaymentPlatformCount — captured results/summary response, .synder-state/recon-preview/api-summary.json.

But there is a better number, and it is available

The quantity that actually changes a decision is how many transactions in this period are imported but not yet synced. Synder documents that state — "Ready to Sync" — and documents exactly what happens if you reconcile anyway: "Reconciling beyond your last sync will surface false 'Missing source' rows."

So instead of "1,200 transactions ready to reconcile" (flattering, meaningless), the screen says "12 transactions in August aren't synced yet. Reconcile now and they'll come back as missing." That is a gate, not a badge. It's the difference between a number the user reads and a number the user acts on.

Evidence Prerequisite: "Transactions already synced for the period you want to reconcile" — Transaction Reconciliation guide. Consequence stated explicitly — TR with Xero.

So two of the four are real. The design consequence: defaults must explain where they came from, and must never assert a fact about the user we haven't measured. "Only clearing account for this connection" is a defensible default label. "Your most-used integration" is not — we'd be making it up.

The six concepts

1

Stop asking for a period. The next one is computable.

A reconciliation is keyed by account + integration + date range, and periods cannot overlap for the same clearing account — gaps are allowed, overlaps are refused with a modal. Which means Synder already knows, exactly, which periods are done and which are open for any given account.

Asking the user to type two dates and then rejecting them is backwards. Replace the date picker with a coverage timeline: months rendered as blocks — reconciled, gap, next up, not settled yet. You pick a gap; you cannot express an overlap, so the overlap error becomes unreachable rather than caught.

This also surfaces the backlog for free. Today a user has no way to see that March and May were never reconciled.

Evidence "Reconciliation periods cannot overlap for the same clearing account" — help docs and Confluence spec, which also specifies the refusal modal and confirms gaps are legal and deleted runs don't block. Today's date cannot be selected at all ("the payment platform may not have finalized today's transactions"). Day-level coverage is derivable from the run list — each record carries its own range.
2

A readiness verdict instead of a volume number.

One strip above the primary action, answering only: can this run produce a trustworthy result? Four inputs, all of them things Synder already knows:

  • Unsynced transactions in the period — the real version of the count we wanted (see above).
  • Connection health — a disconnected platform still appears in the picker today and simply fails during retrieval.
  • Period settled? — today is excluded by rule; platforms hold funds 1–3 business days; Stripe pays out ~2 days after the charge.
  • Overlap — which concept 1 makes structurally impossible.

Green means go. Anything else names the blocker and the fix. This is the same lesson as the run-button work: the value isn't the validation, it's that the user sees it before they commit to something that takes hours.

Evidence Required error copy for a lost connection is specified verbatim in the Confluence spec. Settlement timings and the today-exclusion from the help docs.
3

Pre-declare the transactions that can never match.

Part of every Stripe result is guaranteed noise, and the spec says so: Balance transfers in/out are never synced (status NOT PARSED) so they always land in Missing in accounting, and Reserve transactions cannot be matched at all — not a bug, not fixable this iteration. PayPal Currency Conversion and Account Holds are excluded during normalization. Amazon pre-converted-currency payouts surface as unmatched and the docs call this "expected behavior, not an error."

A period only becomes Reconciled when the Discrepancy and Missing tabs are empty — so today the user has to manually Ignore a pile of rows that were never going to match, with no indication that this was inevitable. Say it up front, and pre-classify them on arrival: "Stripe reserves and balance transfers can't be matched — we'll mark them Ignored so they don't block completion."

This is the biggest available reduction in total time to reconciled, because the slow part isn't the form — it's the resolve loop afterwards.

Evidence Stripe balance-transfer and reserve behaviour, and the PayPal exclusion list, from the Confluence functional spec; Amazon note from the TR guide. Completion rule ("Resolve all transactions in Not matched and Discrepancy to finish reconciliation") from production copy.
4

Start from the account, not the integration — there's already a ticket for this.

DIS-387 · [TxnRecon] Redesign configuration screen (status "One Pager Building") argues exactly this, and also notes that "Automation mode" is really file ingestion mode. Worth reconciling our direction with it rather than proposing in parallel.

The evidence supports the flip, with one caveat. One run = one clearing account. Clearing accounts carry unique connection identity — Stripe mzkt.by (required for Synder) — so picking the account determines the integration, and two fields collapse into one. The caveat: Stripe fees / Stripe sales are shared across all Stripe connections, so the inference only works for clearing accounts. Which is an argument for scoping the list to clearing accounts anyway — something the domain review already flagged as Critical, since a wrong pick produces a meaningless reconciliation with no warning.

Evidence DIS-387 in Confluence (please confirm current status). "One reconciliation run = one clearing account" — DIS-362. Shared-account identity verified against the real 167-account chart of accounts.
5

Don't offer a choice that isn't one.

Only Stripe, Shopify and Amazon support Automated retrieval. PayPal is Assisted only. Every other platform — Square, WooCommerce, eBay, Etsy, Clover and the rest of the ~30 — is Manual: upload any file, map the columns yourself. The method is not a preference, it is a consequence of what the user connected.

So don't render a method selector. Render what Synder is going to do, in a sentence, with one "do it differently" escape. For the Manual-only majority, open directly on the upload with the named report and its steps — never show a dropdown whose other options don't exist for them. For the Automated minority, the sentence is the whole section.

This also fixes something the review caught twice: "Assisted" sits between "Automated" and "Manual" with no explanation, and asks for two files where Manual asks for one — the middle option is more work than the manual one.

Evidence Per-platform capability matrix published in the TR guide and repeated for Summary Sync. Assisted is Stripe and PayPal only per the Confluence spec, with exact file-retrieval steps.
6

Queue the backlog instead of speeding up one form.

A run takes minutes to hours — Stripe "may require up to one hour for large date ranges", and the one real run we captured took about 17 minutes. Meanwhile one run covers one period and one integration, so a user with four unreconciled months and two platforms is looking at eight sequential runs, each configured by hand.

Shaving fields off the form saves seconds against a job measured in hours. The real saving is "You have 4 unreconciled months on this account. Queue all 4." — the coverage timeline from concept 1 makes the set explicit, and the constraints make it safe: the periods are non-overlapping by construction and each produces its own record.

And since the commitment is hours, the button should say so. Not "Run reconciliation" but what it costs and what happens next — the product already emails on completion.

Evidence Runtime from the TR guide; real run createdAt 11:13:48 → lastTransition 11:31:08 in the captured record. The Refresh flow already carries a "Keep existing file" checkbox specifically because Stripe downloads take hours.

Two things worth resolving before any of this gets built

  • Matched % contradiction. The SET acceptance test (TC-POS-01) expects Matched % on the reconciliations list row, and the spec defines the formula. Our own notes record the Matched % column as removed and shipped. One of those is stale — and it matters, because "how done am I" is the signal that brings people back to finish a period.
  • Can Synder's own imported transactions stand in for the platform report? For the ~27 Manual-only platforms the user leaves Synder, exports a file, and maps columns by hand — yet Synder already imported those platform transactions in order to sync them. Whether they can serve as the platform side is an engineering question, not a design one, but it's the one answer that would remove the most work from the most users. Worth asking before we design around the file upload.

Where the evidence is thin

  • No telemetry on what users actually select — integration, account, period or method. Session funnel counts exist; per-field distributions don't. Every "most users…" statement in this document would be an assumption, so none are made.
  • Closed accounting periods appear nowhere in any reconciliation doc or spec, despite being a top cause of sync failure generally. Unknown whether reconciliation interacts with a locked book at all.
  • Re-running a period — duplicate or update? Strong indirect evidence for duplicate (the Refresh tooltip says "Create a new reconciliation for the same time period and same accounts", and a clonedFromReconciliationId field exists) but never confirmed by a live re-run. Logged as open three separate times.
  • "Data is settled" has no product rule. Concept 2 needs one. The settled-month gate currently exists only in our own recon-checks prototype, as a proposal.
  • PayPal and Shopify capability in our prototypes is placeholder data, flagged as such in the files. The published help-doc matrix is the better source and is used here.
