Findings — grouped, most severe first

Critical Bulk actions can fire on a scope the user cannot see

Selection survives tab and filter changes, and unchecking select-all leaves rows selected that are no longer on screen. The confirm dialog names only a count. Rollback and Archive are irreversible in the books.

Evidence — 4 finding(s)
Trust · Critical · confidence 92%
Bulk action bar 'N selected' count + the Archive/Rollback/Cancel confirm dialogs, after a status tab or filter chip changes

Switching a status tab while a selection is live silently re-scopes what the bulk actions will operate on without resetting the bar that reports the selection — the exact FLT-2 shape, moved from filters to selection.

A user who selects all 31 matching transactions, then clicks a tab to double-check something, and hits Rollback gets a dialog naming a number that matches neither their selection nor the visible rows, and destroys records in QuickBooks on a scope they never chose.

Fix: Have every filter, tab, search and page change call clearSelection() (or re-derive the selection against the new result set and re-render the bar), and compute bulk-action scope from the selected ids rather than from currentRows.length.

Trust · Critical · confidence 88%
Bulk-bar master checkbox (chk-all-bulk) after the 'Select all 31' scope escalation

Unchecking select-all leaves 6 invisible transactions selected while every checkbox on screen reads unchecked, and the bulk bar stays armed over that invisible selection.

A user who deselects everything and then clicks Archive or Rollback destroys or hides 6 transactions they believe they deselected, and cannot identify which ones — they sit on page 2, which the pagination bug cannot reach.

Fix: When the master checkbox is unchecked while allSelected is true, clear the entire selection (not just the page), and never leave the bulk bar mounted with a count the user cannot account for on screen.

UX · Medium · confidence 78%
Bulk confirm dialogs + 'Select all N' scope link (#scope-msg → selectAllTotal, index.html:2313-2315)

Destructive bulk confirms identify the selection only by count, and 'Select all' extends it to rows the user has never seen because only 25 of the 31 filtered rows are rendered.

A user who clicks 'Select all 31' then Rollback is asked to approve 'Rollback 31 transactions? The records created in your accounting platform will be deleted' while having laid eyes on 25 of them, so they cannot check what they are about to destroy.

Fix: List or summarise the affected rows in the confirm (e.g. counts by status and integration, plus the out-of-view remainder) instead of a bare number.

UX · High · confidence 80%
table header row / 'Select all on page' checkbox (bulk action bar)

Unchecking 'Select all on page' does not restore the table header row that the bulk bar replaced, so the user is left with a table that has no column headers and no header checkbox.

After backing out of a selection the user loses the column labels and the select-all affordance, so they cannot tell which column is which or re-select rows from the header and must reload the page.

Fix: Tie header-row visibility to selection count so it re-renders as soon as the count returns to 0, and cover the deselect path in the state test rather than only the select path.

Critical "Successful" contains transactions that never reached the books

Skipped and Excluded from sync are grouped under Successful, so the tab count reads as "posted" when it is not. Two lenses hit this independently.

Evidence — 2 finding(s)
Domain (accountant) · Critical · confidence 92%
Status group "Successful" — segmented tab "Successful" and the "Successful" group header in the Status filter panel, which list "Skipped" and "Excluded from sync" alongside "Synced"

"Skipped" and "Excluded from sync" are transactions that were never posted to the books, yet both are grouped under "Successful", so the tab count presents unposted transactions as completed.

At month-end an accountant filters "Successful" to confirm what reached QuickBooks, sees a count of 8, and signs off — while some of those transactions have no entry in the books at all, understating revenue with no visible exception anywhere in the list.

Fix: Move "Skipped" and "Excluded from sync" out of "Successful" into a separate "Not synced (intentional)" group, or rename the group to "Closed" so it no longer asserts the transaction is in the books; this is a book-affecting distinction, so keep the precise wording and add a tooltip rather than simplifying the label.

Clarity (business owner) · Medium · confidence 76%
Status segment tab "Successful" → rows badged "Excluded from sync" and "Skipped"

The "Successful" tab lists transactions whose own status says they were never synced, so the tab label and the row contradict each other on the one question I actually care about.

I cannot answer "is this sale in my books or not?", so I stop trusting the counts and either re-sync rows that were deliberately excluded or ask my accountant to check the whole list manually.

Fix: Rename the group to something that covers both outcomes, e.g. "Completed", and add hover text on these two statuses: "Deliberately not sent to your books — no action needed."

Critical Dashboard tooltip mis-describes Needs attention → duplicate entries

The tooltip calls the group failures only, but it also holds Synced with warnings. Bulk re-syncing that set posts duplicates to QuickBooks.

Evidence — 1 finding(s)
Domain (accountant) · Critical · confidence 85%
Dashboard "Needs attention" card, "?" tooltip above the "50 transactions ›" link that navigates into the filtered list

The tooltip defines the group as failures only, but "Needs attention" also contains "Synced with warnings" and "Deleted with warnings" — transactions that did reach the books.

An accountant told these 50 transactions "failed to sync" will bulk-select them and click "⟳ Sync now", creating duplicate Sales Receipts and Expenses in QuickBooks for every already-synced row in the set.

Fix: Reword the tooltip to describe the group as it is composed — "Transactions that need review: failed, canceled, not parsed, or synced with warnings" — and keep the precise status names in the list rather than flattening them to "failed".

Critical Row-level actions are keyboard-unreachable

The Actions link and every ⋯ menu item are non-focusable elements with no role. The per-row half of the primary task cannot be done without a mouse.

Evidence — 4 finding(s)
A11Y · Critical · confidence 95%
Row actions — the "Sync" / "Retry" / "View sync" link in the Actions column, and every item in the row ⋯ menu

The per-row primary action is an <a> with an onclick and no href, and all ⋯ menu items are plain <div class="dd-item"> — none of them has an href, tabindex or role, so none is in the tab order or operable by keyboard.

A keyboard or screen-reader user cannot sync, retry, roll back or archive an individual transaction at all — the entire per-row half of the primary task is unreachable, leaving only the checkbox-plus-bulk-bar path.

Fix: Make .row-action a real <button> and render each dd-item as a <button role="menuitem"> inside a role="menu", with arrow-key navigation and focus moved into the menu on open and back to the ⋯ trigger on close.

A11Y · High · confidence 90%
Selection controls — 25 .row-chk row checkboxes, #chk-all, #chk-all-bulk, and the "Select all 31" scope link in the bulk bar

None of the 27 selection checkboxes has a label, aria-label or aria-labelledby, and the scope escalation to all 31 rows is an <a onclick> with no href, tabindex or role.

A screen-reader user hears "checkbox, unchecked" twenty-seven times with nothing to say which transaction each one selects, and a keyboard user can never widen selection past the 25 rows on page 1 before firing a bulk Archive or Sync.

Fix: Give each row checkbox an aria-label naming its transaction ("Select Nadia Rahman, $340.00, Failed"), label the two select-all boxes "Select all on this page", and make "Select all 31" a <button>.

A11Y · High · confidence 88%
Bulk action bar replacing the table header row (#head-bulk / #head-normal)

Selecting a row sets #head-normal to display:none, which removes every <th> column name from the table, and the swap is announced by nothing — there is no aria-live region and no focus move.

A screen-reader user who checks a row loses the column names for every cell they then read ("$340.00" with no "Amount"), and is never told that six destructive bulk actions have appeared where the header used to be.

Fix: Keep the header row in the DOM and render the bulk toolbar as a labelled region above the table (role="toolbar" aria-label="Bulk actions") with the selection count in an aria-live="polite" element.

A11Y · High · confidence 85%
Segmented status tabs (All / Needs attention / Ready to sync / In progress / Successful / Deleted)

The tabs are real buttons but expose their selected state only through a CSS class — there is no role="tab"/aria-selected, no aria-pressed and no aria-current anywhere in the file, and the .partial state (segment contains the active status but is narrower than it) has no ARIA equivalent at all.

A screen-reader user cannot tell which status tab is active, so on the deep-linked arrival from the Dashboard — where the Status chip says "Failed" and the tab is only partially selected — they have no way to hear which of the two status controls is actually filtering the rows.

Fix: Wrap the row in role="tablist" with role="tab" + aria-selected on each segment, and render the partial state as visible text in the accessible name (e.g. "Needs attention, 8, narrowed to Failed").

Critical Controls that look live and do nothing

Three of four ⋯ items, Import historical data, Export to CSV, column sort, pagination, rows-per-page and the settings gear all accept a click and return nothing.

Evidence — 6 finding(s)
UX · Critical · confidence 90%
Row ⋯ menu items — 'Sync now', 'Rollback sync', 'Archive'

Three of the four items in the per-row ⋯ menu carry no click handler at all, so choosing them does nothing and the menu gives no response.

A user who opens the row menu to sync, roll back or archive one transaction clicks the item, sees nothing change, and has no way to tell whether the action ran, failed, or was ignored.

Fix: Wire each ⋯ item to the same handler its bulk-bar twin uses (single-row Sync/Rollback/Archive with the same confirm and result message), so the menu commits an action rather than swallowing the click.

UX · High · confidence 80%
Page header button 'Import historical data'

'Import historical data' is styled as a live primary header action but clicking it produces no dialog, no navigation and no feedback of any kind.

A user who arrives filtered to the last 90 days and needs older transactions clicks the one control that promises them, gets silence, and cannot tell whether the click missed, the feature is broken, or an import is running.

Fix: Either wire the button to the import flow or render it disabled with a tooltip stating why, so the header never offers an action that returns nothing.

High Two status controls filter the same dimension with no precedence

The tab row and the Status chip AND together. When they contradict, the list empties and the empty state blames the date range instead.

Evidence — 3 finding(s)
UX · High · confidence 80%
Status filter - reachable only via the "Add filter" menu in the filter bar

The only control that can filter to a specific status is hidden inside the Add filter menu, while the always-visible tab row offers just five coarse groups.

A user who arrives from the Dashboard on one specific status (e.g. one of the several failure statuses inside Needs attention) cannot narrow to it without discovering a nested menu, so they work through a mixed group list instead - the same pattern that produced ~0 dropdown clicks against ~986 tab clicks in Summaries (KF-7).

Fix: Render the Status chip in the filter bar by default with its current value shown, rather than requiring it to be added from the Add filter menu.

UX · High · confidence 75%
Segmented status tab row + Status filter chip (two controls, one dimension)

Two independent controls filter status with no visible precedence, and the documented mitigation (a contradicting tab reads 0) only hides the empty result - it never tells the user the Status chip is what emptied the tab.

A user with a Status chip applied reads "Successful 0" as "I have no successful transactions" rather than "my other status filter excludes them", and stops or re-syncs rows that are already fine.

Fix: Give the tab row precedence over the chip and surface the conflict inline - when a Status chip narrows the tabs, label the tab row "counts limited by Status: <value>" with a one-click clear.

Trust · High · confidence 85%
Empty state ('No transactions in the last 90 days' + 'View all time' primary button) when the Status chip and the status tab contradict

The screen's only zero-row explanation names the one filter that is not responsible whenever the two status controls contradict each other, and its primary remedy cannot resolve it.

A user arriving from the Dashboard on 'Status: Failed' who clicks the 'Ready to sync' tab is told there is no recent activity, widens the date range, still sees nothing, and concludes there is nothing to act on — while failed transactions sit unhandled behind the other control.

Fix: Make the empty state name the filters actually applied and offer the specific one to relax ('No transactions match Status: Failed + Ready to sync — clear the Status filter'), rather than a fixed date-range message with a hardcoded 'most recent transaction' date.

High Row action verbs navigate instead of acting

Evidence — 2 finding(s)
UX · High · confidence 88%
'Actions' column link on every row (label is 'Sync', 'Retry' or 'View sync' depending on status)

The row action link is labelled with an imperative verb but always navigates to the transaction detail page instead of performing the action, while the identical verbs in the bulk bar act on the spot.

A user who clicks 'Sync' or 'Retry' on one row expecting it to sync is taken off the list, loses their filtered position and selection, and has to find the row again — the same word does two different things on one screen.

Fix: Make the row link perform the action in place with the same confirm/result feedback as the bulk bar, and rename the navigational case to an explicit 'View details'.

A user who mis-clicks Sync now — the leftmost button, right where the selection count draws the eye — immediately pushes the whole selection into their accounting books with no chance to back out, even though syncing is the hardest of these actions to undo.

Fix: Give Sync now the same confirm step as the other bulk actions, naming the count and the destination books, or offer an undo window in the result toast.

High Archive promises a restore path that does not exist
